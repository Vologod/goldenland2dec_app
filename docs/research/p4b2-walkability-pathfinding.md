# P4b2: проходимость и pathfinding — статический реверс

Источник: `I:\Games\Златогорье-2\Server.dll` (v1.3, SHA-256
`E3E0A262B1A60DE687523465AD5A36E8`), PE x64, image base `0x140000000`.
Инструмент: Ghidra 12.1.4 (headless). RVA = адрес − `0x140000000`.
Данные: `levels/lvl/l1_1.lvl` из `levels.pak`.

## Проходимость из LVL (memory-verified)

- Тайл: `u16 relief`, `u16 sound`, `u16 mask` (см. `formats.md`), по умолчанию
  `mask = 0xFFFF`; поле `mask` для движения **не используется**.
- Чанк LVL = 2×2 тайла. Файл хранит чанки **column-major**: индекс чанка
  `cx * chunk_height + cy` (загрузчик обходит столбцы снаружи, строки внутри).
- Ключевое слово чанка — первая запись тайла:
  `word = uint32(tile[0].relief) | (uint32(tile[0].sound) << 16)`
  (эквивалентно битам 8..11 `tile[0].relief`). Остальные три записи чанка
  загрузчик тоже сохраняет, но геттер движения их не читает.
- Для world-тайла `(x, y)`: `sub = (x & 1) + 2 * (y & 1)`;
  `blocked = (word & (0x100u << sub)) != 0`; `walkable = !blocked`.
- `l1_1.lvl`: 115×112 чанков = 230×224 тайла = 51520; заблокировано
  **18028** (≈35 %). Проверено real-тестом `tests/game/test_walk_grid.cpp`.
- Мир (`DAT_14088e30`) отдаёт блокировку через виртуальный `+0x64(x, y, flag)`:
  ненулевое значение — клетка заблокирована для флага. Флаги: `0x100` — движение,
  `0x1000` — обзор. `+0x70(x, y)` — проверка границ; `+0x48(&w, &h)` — размер мира.

## Динамическая занятость

- `DAT_14088dac` — массив `int` по клеткам, инициализируется `-1` (пусто) в
  `FUN_14012b18` (RVA `0x12b18`). Установка/чтение: `FUN_14012cdc` (`0x12cdc`),
  `FUN_14012d00` (`0x12d00`), `FUN_14012d2c` (`0x12d2c`).
- При поиске пути клетки с `grid != -1` (кроме собственной) считаются занятыми
  (`FUN_14010d38`, `FUN_14015b48`), т.е. NPC обходят друг друга.

## Проверка ходьбы и поиск пути

- `FUN_1401c334` (RVA `0x1c334`) — «клетка проходима»: границы + `+0x64(...,0x100) == 0`.
- `FUN_1400fb1c` (RVA `0xfb1c`) — «клетка свободна для сущности»: `grid == -1` или
  `grid == self`, и `+0x64(...,0x1000) == 0`.
- `FUN_14012d4c` (RVA `0x12d4c`) — валидация прямой линии A→B: идёт по клеткам
  (Брезенхэм с дробным шагом) и возвращает 0 при первой заблокированной/занятой
  клетке.
- `FUN_14010d38` (RVA `0x10d38`) и `FUN_1400ffd4` (RVA `0xffd4`) — построение поля
  расстояний (Dijkstra/волна) по 8 направлениям от стартовой клетки; массив стоимостей
  `+0x14`, массив предков `+0x10` (пары клеток). Заблокированные и занятые клетки
  исключаются.
- `FUN_14015b48` (RVA `0x15b48`) — проверка соседней клетки при следовании пути.
- Прямая ходьба используется, если линия свободна: персонаж идёт по прямой к цели,
  без промежуточных waypoint-ов в центрах клеток; иначе строится путь и персонаж
  идёт по waypoint-ам (см. `FUN_14020444`/`FUN_14021754`, `p4b-person-movement.md`).

## A* (проверено 2026-10-22)

- Стоимость шага — **10** для всех 8 направлений; диагональ стоит столько же,
  сколько ортогональ.
- Эвристика `h = max(dx,dy) + 0.375 * min(dx,dy)`; константа `0.375` прочитана из
  `Server.dll` (`0x1408c500`). Итоговая оценка `f = g + 12*h`, т.е. вес `1.2` при
  шаге 10 (в нормализованных единицах: `h' = max + 0.375*min`, `f = g' + 1.2*h'`,
  `g'` — число шагов).
- Диагональ разрешена без проверки двух ортогональных соседей: проверяется только
  клетка назначения.
- В порте сохранены эти параметры. Точный порядок перебора соседей и разрешение
  ничьих (FIFO по порядку вставки в порте) могут отличаться от оригинала —
  задокументированный остаточный риск.

## Отклонения порта (D-028)

- Терраин-костов в данных нет; вместо Dijkstra с костами — A* с шагом 10
  (в порте нормирован в 1) и эвристикой `max + 0.375*min` с весом 1.2, те же
  8 направлений.
- Бит обзора `0x1000` не моделируется.
- Динамические препятствия (двери/триггеры) не входят в P4b2.

## Уточнение (2026-10-22, memory-verified): откуда берутся флаги

- Мировой объект создаётся в `GoldenLand.exe`: `FUN_0042ca7c` → `FUN_00427890`
  (vtable `0x484a00`); указатель кладётся в engine-интерфейс `+0xa4`
  (`DAT_00469d64`), откуда его читают `GetServerAPI`/`GetClientAPI`.
- Слот vtable `+0x64` = `FUN_00426234` (проверка флага):
  `sVar = (x&1) + 2*(y&1); return grid[col(x>>1)][(y>>1)*0x28] & (flag << sVar);`
  Ненулевое значение = заблокировано. Слоты `+0x68`/`+0x6c` — сеттер/переключатель
  флага, `+0x78` (`FUN_00426430`) — установка флага для списка клеток cell-group,
  `+0x7c` (`FUN_00426490`) — загрузка уровня.
- `FUN_00426490` читает `BLK_MHDR` по 4 записи `u32+u16` на чанк и кладёт `u32`
  каждой записи в `colptr + row*0x28 + tile*4` (геттер читает только `tile=0`,
  `+0x64`). Чанки читаются **column-major** (столбцы снаружи, строки внутри),
  поэтому файловый индекс чанка — `cx*chunk_height + cy`, а не `cy*chunk_width+cx`.
- Отсюда рабочее правило: `word = uint32(tile[0].relief) | (uint32(tile[0].sound)<<16)`,
  `blocked = (word & (0x100u << sub)) != 0`, `sub = (x&1) + 2*(y&1)`.
- Проверка ground truth (2026-10-22): чтение live-памяти запущенного
  `GoldenLand.exe` через `ReadProcessMemory`: `world = [exe+0x69d64]`,
  `grid = [world+0x330]`, размеры `world+0x320/+0x324`, обход `grid[col]+row*0x28`
  и бит `0x100<<sub`. Реконструкция из LVL совпала с live-сеткой **точно**
  (0/51520 расхождений после загрузки уровня). В рантайме двери/скрипты меняют
  ~331 клетку (0.6 %); это вне P4b2.
- Прежние выводы (бит `0x100` поля `mask`; «флаги движения не хранятся в LVL»)
  ошибочны: использовались неверное поле (`mask`) и row-major порядок чанков.
