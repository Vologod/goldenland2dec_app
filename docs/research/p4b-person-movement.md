# P4b: движение NPC — статический реверс `Server.dll`

Источник: `I:\Games\Златогорье-2\Server.dll`, v1.3, SHA-256
`E3E0A262B1A60DE687523465AD5A36E8` (см. `00-game-build.md`). PE x64, image base
`0x140000000`. Инструмент: Ghidra 12.1.4 (headless), декомпилятор. RVA ниже — это
виртуальные адреса, т.е. RVA = адрес − `0x140000000`.

## Типы маршрутов

`FUN_1401f9bc` (RVA `0x1f9bc`) разбирает строку `route_type`:

| Строка | Значение |
|---|---|
| (по умолчанию, в т.ч. `STAY`) | 0 |
| `STAY_ROTATE` | 1 |
| `MOVED` | 2 |
| `MOVED_FLIP` | 3 |
| `RANDOM_RADIUS` | 4 |
| `RANDOM` | 5 |

## Разбор SEF

`FUN_1401edc4` (RVA `0x1edc4`) — секция `persons:`. Поля пишутся в объект Person:

| Смещение | Поле |
|---|---|
| `+0x40` | `literary_name` |
| `+0x44` | тип literary name |
| `+0x5f8/+0x5fc` | `position` (тайлы), spawn |
| `+0x151c` | `route_type` (enum выше) |
| `+0x1520` | `radius` |
| `+0x1524` | `route` (имя `cell_group`) |
| `+0x2668/+0x266c` | `delay_min` / `delay_max` |

`FUN_140222d0` (RVA `0x222d0`) переводит тайлы в пиксели:
`px = tile_x * 12 + 6`, `py = tile_y * 9 + 4`; эти же значения — «центр» клетки.
Позиция также хранится как float (`+0x4fc/+0x500`, `+0x628/+0x62c`) и как тайлы
(`+0x604/+0x608`).

## RNG (CRT `rand`)

`_rand` (RVA `0x6c09f`) — стандартный MSVC CRT `rand` с одним глобальным состоянием:
`state = state * 0x343FD + 0x269EC3` (mod 2³²), результат `(state >> 16) & 0x7FFF`.
В `Server.dll` нет вызова `srand`, поэтому начальное состояние — **1** (MSVC default).
Все NPC используют один поток; порядок вызовов между NPC — порядок их обновления.

`FUN_140061e4` (RVA `0x61e4`) — `rand(min..max)`: если `max <= min` → `min` (без расхода
`rand`); иначе `min + round((max - min + 0.99999) * rand / 32767.0)`, округление FPU
к ближайшему (round-to-nearest). Из-за `0.99999` при `rand = 32767` результат может быть
`max + 1`; это поведение оригинала, порт его сохраняет.

`FUN_14006288` (RVA `0x6288`) — `coin(p)`: `p <= 0` → false; `p > 1` → true; иначе
`rand / 32767.0 < p`. Для 50/50 `coin(0.5)` = `rand / 32767.0 < 0.5`.

Порядок: на прибытии/после паузы сначала бросается пауза (`FUN_1401c378` →
`FUN_140061e4`), затем выбирается цель (`FUN_1401c93c`): `MOVED_FLIP` бросает
`coin(0.5)` для `±1`, `RANDOM*` — две выборки `rand` на попытку (`FUN_1401c2a0`).

## Выбор следующей цели

`FUN_1401c93c` (RVA `0x1c93c`), «Next moved»:

- Маршрут: указатель `+0x162c`, индекс `+0x1630`, количество клеток `+0x190`
  относительно ресурса маршрута.
- `MOVED` (2): если `index >= count`, `index = 0`; цель = `route[index]`; затем
  `index++`. Движение по кругу.
- `MOVED_FLIP` (3): если `index < 0 || index >= count`, `index = 0`; цель =
  `route[index]`; затем `index += (rand(0.5) ? 1 : -1)`, где `rand(0.5)` —
  `FUN_14006288` (50 %). Случайное блуждание вдоль маршрута.
- `RANDOM_RADIUS` (4): цель = случайная точка вокруг **spawn** (`+0x5f8/+0x5fc`).
- `RANDOM` (5): цель = случайная точка вокруг **текущей** позиции (`+0x604/+0x608`).
- `STAY` (0): если позиция смещена от spawn, идёт назад к spawn; иначе стоит.
- `STAY_ROTATE` (1): поворот на месте; в `l1_1` не встречается.

### Индекс маршрута: сдвиг при выборе (A2)

Индекс маршрута (`+0x1630`) сдвигается в момент выбора цели, до планирования пути и
движения:

- `MOVED`: `target = route[index]`; затем `index = (index + 1) % count`.
- `MOVED_FLIP`: если `index < 0 || index >= count` → `index = 0`; `target = route[index]`;
  затем `index += coin(0.5) ? +1 : -1`.

`consume_goal` (прибытие) индекс не меняет — только сбрасывает `has_goal` и
per-goal состояние. Если планирование пути к только что выбранной клетке не удалось
(клетка заблокирована/недостижима), цель сбрасывается, и следующая попытка берёт
следующую клетку маршрута. Повторное планирование в середине пути (клетку занял другой
NPC) цель сохраняет и повторяет, пока путь не построится.

Live-память `GoldenLand.exe` v1.3, `L0.P744_oficer1` (`MOVED`, `track3`):

- в момент, когда NPC стоял в предыдущей клетке, `+0x1630` уже указывал на следующую
  клетку — сдвиг происходит на выборе, а не на прибытии;
- `route[0] = (186,147)` в live-сетке заблокирован, но NPC не зациклился на нём:
  после неудачного планирования выбор ушёл дальше, и NPC дошёл до `route[2] =
  (143,151)` — заблокированная цель не retry-ится бесконечно;
- статическая реконструкция `l1_1` из LVL (D-028) считает все 8 клеток `track3`
  проходимыми; блокировка `route[0]` в live — динамическая (двери/скрипты, ~331
  клетка), поэтому в порте этот NPC идёт в `route[0]`. Пропуск заблокированной клетки
  проверяется синтетическим unit-тестом.

Случайная точка — `FUN_1401c2a0` (RVA `0x1c2a0`):

- база: spawn (`+0x5f8/+0x5fc`) для `RANDOM_RADIUS`, текущая позиция
  (`+0x604/+0x608`) для `RANDOM`;
- `r = +0x1520`, при `r == 0` берётся 13;
- если базовая клетка вне карты (`+0x70 == 0`) — возвращается база без выборок;
- иначе цикл: `dx = rand(-r..r)`, `dy = rand(-r..r)` (в тайлах); кандидат
  принимается, если `FUN_1401c334` подтверждает границы и проходимость
  (мир + маска `0x100`). Занятость другими NPC не проверяется, лимита попыток
  в оригинале нет;
- на неудачном построении пути для `RANDOM*` следующая попытка выбирает новую
  случайную цель: счётчика из 3 неудач нет.

Занятость других NPC при выборе цели не проверяется. Собственная цель
(`state.goal` при `has_goal`) исключена из occupancy в `blocked_for` и
`tile_occupied` для **всех** route-типов (`MOVED`, `MOVED_FLIP`, `RANDOM*`), а не
только для `RANDOM*`; это освобождение цели, а не резервирование. Поэтому NPC
может проложить путь в клетку, занятую другим NPC, и встать поверх него;
abort/повторной выборки не происходит. Оригинал, по описанию, считает чужие
клетки занятыми без исключения для цели — это остаточное расхождение C12
(`docs/research/parity-audit-p4.md`), unverified.

Порт повторяет цикл без лимита. Единственный предохранитель — технический
потолок 1'000'000 выборок с warning (level/person/base tile; повторно для той же
вырожденной цели не пишется) и откатом на базовую клетку; это защита от
вырожденной карты, а не изменение наблюдаемого поведения. `MOVED`/`MOVED_FLIP`
сохраняют прежнюю обработку неудачного планирования (D-031).

## Пауза после прибытия

`FUN_1401c378` (RVA `0x1c378`):

1. Если `now < wait_until (+0x1634)` — ждать.
2. Иначе, если флаг ожидания (`+0x1638`) не выставлен: `d = rand(delay_min..delay_max)`
   (`FUN_140061e4`, inclusive-ish CRT `rand`).
   - `d < 500` → паузы нет, сразу следующая цель;
   - иначе `wait_until = now + d`, флаг = 1, ждать.
3. По истечении — сбросить флаг и продолжить.

Время `now` — `DAT_14088e1c`, миллисекунды.

## Прибытие и скорость

`FUN_14021754` (RVA `0x21754`) и `FUN_14020444` (RVA `0x20444`):

- Цель — центр клетки в пикселях; прибытие, когда `|dx| < 4` и `|dy| < 4` px.
- `FUN_1401fef8` (RVA `0x1fef8`) записывает скорость в `+0x584/+0x588` и модуль в
  `+0x158`.
- Скорость берётся из выбранной анимации `_go`: поля `+8/+0xc` дескриптора
  соответствуют `movement_x/movement_y` PAD. Реальные значения `l1_1`:
  `6.0..6.916667` px и `5.0` px; `delay` `_go` = 80/85 мс.
- Диагональ: `fx² = dx²/(dx²+dy²)`,
  `speed = (1-fx²)*movement_y + fx²*movement_x`;
  `vx = dx/len * speed`, `vy = dy/len * speed`.
- Константы перевода: `1/12 = 0.0833333`, `1/9 = 0.1111111`.
- `_go` содержит 16 направлений. `FUN_1402085c` (RVA `0x2085c`) по знаку и
  абсолютным компонентам единичного вектора возвращает код 10..25; пороги:
  `0.2079`, `0.5878`, `0.8616`, `0.9863`.
- `FUN_14020e64` (RVA `0x20e64`) переводит 16 кодов в 8 направлений:
  `10→0`, `11..13→1`, `14→2`, `15..17→3`, `18→4`, `19..21→5`, `22→6`, `23..25→7`.
  Обратно `FUN_14020e14`: `0→10`, `1→12`, `2→14`, `3→16`, `4→18`, `5→20`,
  `6→22`, `7→24`.
- `FUN_1401fb1c` (RVA `0x1fb1c`) — строки SEF `UP, UP_LEFT, LEFT, DOWN_LEFT, DOWN,
  DOWN_RIGHT, RIGHT, UP_RIGHT` → 0..7 (совпадает с P4a).

## Live-измерение скорости (A5)

Метод: запущенная `GoldenLand.exe` v1.3, уровень `l1_1`. Объекты Person мира
найдены по строке имени в `+0x4c`; позиция снималась как float `+0x4fc/+0x500`,
тайл — `+0x604/+0x608`. Значения читались по кадрам, интервалы — по времени
между соседними обновлениями позиции.

- Шаг за одно обновление равен ровно `iso_speed(dx,dy,move_x,move_y)` из `_go`:
  `L0.P744_oficer1` (move 6/5) — **5.254 px**, `L0.P692_citizen5` (move 4/3) —
  **3.862 px**.
- Интервал обновления масштабируется от `delay` go-анимации с коэффициентом
  **0.8**: `L0.P744_oficer1` (delay 80 мс) — среднее ~63 мс;
  `L0.P692_citizen5` (delay 85 мс) — ~68 мс. Интервалы квантуются тиками
  35 Гц (56/84 мс).
- Из памяти процесса: `sv_fps = 35`, `sv_game_speed = 0`, `gv_anim_speed = 0`.
- Отсюда `speed_px_s = iso_speed(...) * 1000 / (go_delay_ms * 0.8)` — прежняя
  формула × **1.25**. Порт сохраняет интеграцию 1/60 с; оригинал квантует
  обновления к 35 Гц.

## Частота обновления

`sv_fps` по умолчанию **35** (регистрация в `FUN_14003884`, RVA `0x3884`:
`0x23`), `sv_game_speed` — 0..4. Точная частота вызова обновления Person
(`FUN_14020260`, RVA `0x20260`) статически не закреплена (вызов виртуальный),
но live-измерение при `sv_game_speed = 0` даёт интервал `delay * 0.8`,
квантованный к 35 Гц. Принятое решение D-033:
`speed_px_s = iso_speed(...) * 1000 / (go_delay_ms * 0.8)`; в порте шаг 1/60 с.

## Занятость (occupancy) — A6

Источник тот же: `Server.dll` v1.3, SHA-256
`E3E0A262B1A60DE687523465AD5A36E8`, RVA = адрес − `0x140000000`.

- `DAT_14088dac` (RVA `0x88dac`) — клеточная сетка занятости сущностями. Запись/чтение
  идут из **текущих позиций** сущностей (`FUN_14012cdc`, RVA `0x12cdc`;
  `FUN_14012d2c`, RVA `0x12d2c`) и пересобираются на каждом обновлении. Резервирования
  будущих/путевых клеток нет.
- `FUN_14020a18` (RVA `0x20a18`) — коллизия движения: проверяются клетки, в которые
  персонаж собирается войти, против сетки занятости (плюс собственная клетка). Цели и
  клетки пути не зарезервированы.
- Порт до A6 изобретал `mark_occupied(path.back())` при планировании и
  `mark_occupied(path[path_index])` после каждого шага. В A6 оба вызова удалены:
  `rebuild_occupancy` каждый тик строит сетку из текущих тайлов, после хода помечается
  только `tile_of(m)` (чтобы персоны с бо́льшим индексом в том же тике видели новую
  позицию). Освобождённая клетка внутри тика не очищается: до следующего
  `rebuild_occupancy` occupancy содержит текущие тайлы плюс только что занятый тайл.
  Регрессионный тест — `same-tick planning ignores another NPC's reserved goal cell`
  (`tests/game/test_level_simulation.cpp`): два NPC планируют в одном тике, цель
  первого — единственный проход на маршруте второго; план второго успешен и проходит
  через эту клетку, пока первый ещё не дошёл до неё. На коде с `mark_occupied(path.back())`
  план второго не строится.

### Измерение A6 (`l1_1`, 180 с, seed 1)

Временная инструментация на ветке occupancy-abort (удалена до коммита) писала для
`L0.P692_citizen5` заблокированную клетку, тип блокировки (текущая позиция / резерв
`path_index` / резерв цели) и обе персоны.

- До правки: **110** occupancy-abort у P692; **все 110** — попытка войти в `(143,151)`,
  блокирует **текущая** клетка `L0.P744_oficer1` (`1722,1363`); ни одного abort из-за
  резерва waypoint/цели. Stability: 113 aborted-переходов.
- После удаления резервирований: те же **110** occupancy-abort / **113** aborted;
  у остальных NPC без изменений (`P678=3`, `P640=5`, суммарно без P692 — 8). Значит,
  резервирования не были причиной конфликта A5.
- Механизм (t=19033): P692 в `(1717.528,1358.220)` = тайл `(143,150)`, путь
  `(144,134)->(142,158)`. На следующем тике replan даёт путь
  `(143,150),(142,151),...,(142,158)`, waypoint — центр `(1710,1363)`. Диагональный шаг
  из `(1717.5,1358.2)` к `(1710,1363)` даёт сырой `tile_at(next)=(143,151)`: x остаётся
  в колонке 143 до `x<1716`, а y уже перешёл границу строки 151 (`1358.5`). То есть
  персонаж задевает угол занятой клетки `(143,151)`, хотя waypoint — `(142,151)`.
  Остановки повторяются t=19033…22667 (~3.6 с), пока `oficer1` не уйдёт.
- Это согласуется с `FUN_14020a18` (проверка клетки, в которую входят): доказательств,
  что оригинал обрабатывает corner clipping иначе, нет, поэтому правило входа не
  менялось. Порог stability для P692 оставлен `<150` и не ослаблялся дальше.

## Что не подтверждено

- Точная формула `STAY_ROTATE` (тип 1) и `RANDOM` (тип 5) за пределами выбора цели.
- Поведение при отсутствии `_go` (в `l1_1` у движущихся NPC анимация есть).
