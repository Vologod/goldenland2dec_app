### E2. `sv_fps` consumer: host tick gate

No direct read of the `sv_fps` entry was found in `Client.dll` or
`Server.dll` by exact-symbol search (indirect config access is not
exhaustively ruled out). The only direct consumer found is a virtual method
in `GoldenLand.exe`:

- Function start VA `0x4184ac` (RVA `0x184ac`); address is stored as a data
  pointer at VA `0x482080` (RVA `0x82080`, file `0x4f080`), i.e. indirect
  dispatch; there is no direct `call 0x4184ac` in the executable.
- Reads the fps entry value twice:
  - VA `0x4184d7` (RVA `0x184d7`): `movl 0x469bb8,%eax; movl 0x8c(%eax),%edx; test %edx,%edx; je …`
  - VA `0x4184ef` (RVA `0x184ef`): `movl 0x469bb8,%edx; movl 0x8c(%edx),%ecx`
- Gate formula in the same function:

```
4184e6: movl 0x18(%esp),%ecx        ; time object passed as argument
4184ea: calll 0x408fd4              ; eax = *(int*)time_obj  (ms-like value)
4184ef: movl 0x469bb8,%edx          ; fps entry
4184f5: movl 0x8c(%edx),%ecx        ; ecx = sv_fps
4184fb: ... fildl / fadds 0x481dd0(,%eax,4) / fsubs 0x4(%edi)
41850e: movl $0x3e8,%eax            ; eax = 1000
418513: xorl %edx,%edx
418515: idivl %ecx                  ; eax = 1000 / sv_fps  (integer division)
41851b: fildl 0x8(%esp)
41851f: fcompp                      ; compare interval with elapsed
418524: jbe 0x41852d               ; interval <= elapsed -> run tick
```

- `sv_fps == 0` skips the gate entirely (jump to the tick path).
- When the gate passes, the method calls `vtable+0xc` on `this`, increments a
  frame counter at `0x9160(%edi)`, and stores the current time to the float
  field `0x4(%edi)` (VA `0x41852d`–`0x418568`, RVA `0x1852d`–`0x18568`).
- For the default/live value 35 the integer division yields **28**
  (`1000 / 35`, truncated), and the run condition is `elapsed >= 28`
  (`jbe` on the interval-vs-elapsed compare).
- The time value comes from a one-field getter `VA 0x408fd4`
  (`movl (%ecx),%eax; ret`) over an argument object; the clock that fills
  that object is **not** resolved in this task (Task 2).

This is the comparison threshold used by the host tick gate. It is **not** a
claim about the final effective period: frame pacing/accumulator, QPC
quantization and the update of the time object still belong to Task 2.

## Tick model

Task 2 result: the original does **not** use a continuous
`1000/35 = 28.571 ms` step and has **no fixed-step accumulator**. A
free-running host frame loop calls a gate whose threshold is the signed
integer division `1000 / sv_fps`; for the default/live 35 this is **28 ms**.
The disassembly proves this threshold and the per-frame gate, **not** that
the server always ticks every 28 ms. The Server.dll tick runs at most once
per host frame, and `last_ms` is reset to the tick-start clock sample (no
catch-up). With host frame time `F` (integer-ms clock), the effective period
is `F*ceil(28/F)` for `F < 28 ms` (idealized; floor-ms sampling shifts the
grid by ~1 ms) and `F` for `F >= 28 ms`; exactly 28 ms only when the frame
grid lands on 28. There is **no max-frame clamp**: if `F > 28 ms`, the
server slows to `F` with no multi-tick catch-up.

### T1. Main loop and frame schedule (`GoldenLand.exe`)

- Frame-loop function starts at VA `0x42dce8` (RVA `0x2dce8`); inner frame
  loop `0x42de9a`–`0x42dedb` (RVA `0x2de9a`–`0x2dedb`); outer restart loop
  `0x42de0d`–`0x42df60` (RVA `0x2de0d`–`0x2df60`).
- Per iteration (addresses are VAs):

  ```
  42de9a  ecx=&timer(0x46d800); call 0x408ff0   ; refresh timer
  42dea4  call 0x42e074                         ; PeekMessage drain, non-blocking
  42dea9  ecx=[0x469a08]; eax=[ecx]; push &timer; call *0x10(eax)  ; server gate 0x4184ac
  42deb9  ecx=[0x454a48]; eax=[ecx]; push &timer; call *0x10(eax)  ; client update 0x40fc2c
  42dec9  ecx=[0x454800]; call 0x40a1cc         ; render
  42ded4  if [0x46c2ec]==0 jmp 42de9a           ; quit flag
  ```

- No `Sleep`, no `WaitMessage`, no `GetMessage`: `0x42e074` is a
  `PeekMessageA(..., PM_REMOVE)` drain (IAT `0x4431a8`) and returns
  immediately. The host imports only `QueryPerformanceCounter`,
  `QueryPerformanceFrequency` and `GetTickCount` (Task 1 E4). Host-side
  pacing is therefore a busy loop; any blocking can only come from inside
  the render/client call chain (U1).
- `0x469a08` is the gated world object: vtable `0x482070` (RVA `0x82070`),
  allocated at `0x42d616` with size `0x123c0`, constructor `0x41b560`,
  stored to `0x469a08`. Its gated path calls the Server.dll API and the
  world/entity update, i.e. it is the single-player server-side world.
  `0x454a48` is the client object (vtable `0x4813c8`); its `+0x10`
  (`0x40fc2c`) is **not** `sv_fps`-gated (it only checks `0x469bc4` and
  otherwise runs every frame).

### T2. Clock

Timer object `0x46d800` is a plain struct (no vtable):

- ctor `0x409050` (RVA `0x9050`): `QueryPerformanceFrequency` → `+0x18`,
  then `0x408fd8` zeroes `+0`/`+4` and `QueryPerformanceCounter` → `+0x8`.
- update `0x408ff0` (RVA `0x8ff0`): `QueryPerformanceCounter` → `+0x10`,
  computes `(now - start) / freq` in x87, stores float seconds at `+4`,
  multiplies by the double `1000.0` at VA `0x47f858`, sets FPU RC=`0xC00`
  (truncate) and `fistpll`, then stores the low dword at `+0`.
- getter `0x408fd4` (RVA `0x8fd4`) is `movl (%ecx),%eax; ret`.
- The QPC start pair at `+0x8/+0xc` is never rewritten after the ctor; `+0`
  is an **absolute** millisecond clock since timer creation, not a per-frame
  delta. Truncation is applied to the absolute value, so there is no
  cumulative truncation drift (<1 ms absolute).
- The unsigned-to-float conversion is at `0x418501`/`0x418504` using the
  table VA `0x481dd0` (`0.0`, `4294967296.0`).
- `+0` is stored as 32-bit (`movl %eax,(%edi)`), so it wraps after
  `2^32 ms` (~49.7 days) — U2.

### T3. Gate formula (`0x4184ac`, RVA `0x184ac`)

```
4184b2  if (this->0x212c == 0) return;                 ; world not running
4184d7  if (sv_fps (0x469bb8->+0x8c) == 0) goto tick;   ; gate disabled
4184e6  eax = timer->ms                                  ; via 0x408fd4
        st0 = (float)(uint32)eax                         ; fildl + 2^32*sign
41850b  st0 = st0 - this->last_ms (float at +4)          ; elapsed
41850e  eax = 1000; edx = 0; eax = eax / sv_fps          ; idivl, signed trunc
41851b  st0 = (float)interval; fcompp                     ; interval vs elapsed
418524  jbe tick                                          ; if interval <= elapsed
        return
tick:
418532  call *0x46d82c(timer)                             ; Server API slot +0xc
41853a  this->tick_index++ (0x9160)
418541  this->vtable[+0xc](this)                           ; world update 0x418328
418546  this->last_ms = (float)(uint32)timer->ms           ; same sample
```

- `1000 / sv_fps` is signed `idivl`, i.e. C truncation toward zero. For
  `sv_fps=35` the result is **28**; the value 28.571 is never formed.
- Both operands are exact small integers converted to float, so the test is
  effectively `elapsed_ms >= interval_ms`.
- `this+4` (`last_ms`) is initialized to 0 by vtable slot 0 (`0x417f48`,
  RVA `0x17f48`, writes at `0x417f53`) and again by world init `0x418600`
  (`0x41871a`).
- There is no second accumulator, no remainder carry and no `while`
  catch-up: at most one Server API tick and one `0x418328` pass per loop
  iteration.
- The `last_ms` sample is taken **before** `*0x46d82c` and the world update
  and is not refreshed inside the tick: both API entries only read
  `*(int*)timer` (`FUN_14007cc4`, decompiled.c:6041; and the client entry
  uses `FUN_1201aed8`, client decompiled.c:20654, which is also
  `movl (%ecx),%eax; ret`). Therefore `last_ms` is the tick-start sample,
  not tick-end wall time.

### T4. Server tick identity and time base

`GetServerAPI` (`Server.dll` RVA `0x5cbf0`, only export;
`server/decompiled.c:63133`) fills the host table `0x46d820`:
`+0`=0, `+4`=`0x1405cd60`, `+8`=`0x1405cb94`, `+0xc`=**`0x1405cbc4`**,
`+0x10`=heap object (decompiled.c:63154–63156, 63180). The gate call
`*0x46d82c` is therefore Server API slot `+0xc`:

### T5. Derived period / effective rate

- Threshold: `T_min = trunc(1000 / sv_fps)` ms. `sv_fps=35` → `T_min = 28`.
  This is a **minimum** between tick starts, not the period itself.
- Tick condition: `clock_ms - last_ms >= T_min`; `clock_ms` is sampled once
  per host frame and `last_ms` is the sample at the start of the previous
  tick. At most one tick runs per frame (T3), so the achievable period is
  quantized by the host frame grid.
- Let `F` be the host frame time. For `F < 28 ms` the idealized period is
  `F*ceil(28/F)`; the actual floor-ms grid is that value ±1 ms (e.g.
  `F≈16.7 ms` gives a ~33–34 ms grid/average, not exactly 33.3 ms).
  Exact 28 ms (`35.714 Hz`) occurs only when the frame grid lands on 28
  (e.g. `F` an integer divisor of 28). This is **not** a 28.571 ms/35.0 Hz
  continuous step.
- For `F >= 28 ms`, at most one tick runs per frame, so the period is `F`:
  the server slows to the frame rate and falls behind wall time. There is
  no max-frame clamp and no multi-tick catch-up.
- Whether the live original is ~35 fps (`F ≈ 28 ms`) is a **hypothesis**
  pending U1; D-033 is consistent with a ~28 ms grid but does not measure
  the host frame time.
- `sv_game_speed` does not participate: it is only an additive term to the
  animation frame delay `entity+0x55c` in `set_speed`/`FUN_1400e5c8`
  (Task 1 E3), and the live value is 0.

### T6. `sv_fps` edge cases (static)

- `sv_fps == 0`: gate skipped (`je 0x41852d`); server ticks every host frame
  and still receives fresh ms each frame.
- `sv_fps < 0`: signed `idiv` gives a negative interval, so
  `elapsed >= interval` is always true → tick every frame.
- `0 < sv_fps < 1000`: truncation runs faster than nominal for non-divisors
  (60 → 16 ms = 62.5 Hz; 30 → 33 ms = 30.3 Hz).
- `sv_fps = 1000`: interval 1 ms (gate still applies).
- `sv_fps > 1000`: interval 0 → tick every frame.
Only 35 is confirmed live (D-033); the rest is static (U5).

### T7. First tick and `tick_index`

- `last_ms=0` at reset; the timer is created earlier (`0x42c96a`), so after
  DLL load/init the first gate normally fires on its first frame
  (elapsed-since-ctor > 28 ms).
- `tick_index` = `world+0x9160`: reset to 0 by vtable slot 0 (`0x417f48`),
  incremented once per executed tick **before** the world update
  (`0x41853a`). It is an independent 32-bit counter (not derived from ms),
  used as a 16-slot ring index (`&0xF`, e.g. `0x418d34`, `0x41687e`) and
  sent/pushed to the other side (`0x418d7e` → `0x41286c`).
- At `sv_fps=35` the minimum sampled interval between counter steps is
  28 ms; the actual step is frame-quantized (T5). There is no
  fractional/partial tick index.

### T8. D-033 cross-check

D-033 live `l1_1` evidence: `go` delays 80/85 ms become raw **~63/~68 ms**
after the 0.8 factor; D-033 also **derived** 56/84 ms under the 35 Hz
assumption.

- The 56/84 figures are a derived expectation, not an independent
  measurement: the raw averages are ~63/~68 ms and are not exact multiples
  of 28.
- They are **consistent with** the 28 ms gate threshold (the raw values lie
  between 2×28 and 3×28 ms), but on their own they do **not** distinguish
  28.0 ms from 28.571 ms.
- The decisive evidence is the disassembly: signed `idivl` truncation makes
  the threshold 28 ms and thereby rules out the continuous 28.571 ms model.
  D-033's ~35 Hz observation also disfavors a 1/60 s step, but that is not
  needed for the threshold.
- The effective frame grid in that capture remains U1.

## Consumers

Task 3 result: with one exception, the original's per-entity consumers are
**millisecond deadlines/accumulators**, not tick counts. `DAT_14088e1c`
(server "now", ms) is latched once per executed server tick (T4) and all of
movement, animation, pause, spawn and script timers compare/accumulate
against that same ms value. Changing the host rate to 35 Hz therefore
changes **sampling/quantization**, not the nominal delays. The exception
is AI think/see: they run once per entity-update invocation, which becomes
**once per tick** only if the unverified vtable-slot link in U-C5 holds;
in that case their decision frequency would change with the tick rate.
Restock's internal cadence is likewise unresolved (U-C2).

### C1. Time source for every consumer

All deadlines below use `DAT_14088e1c`, written by Server API slot
`0x1405cbc4` from the host QPC-derived integer-ms timer (`decompiled.c`
line 63156, `param_2[3] = &LAB_1405cbc4`; see T4). The value is an
absolute ms clock latched at each executed tick; no consumer calls the
host clock directly. `sv_fps` only gates how often this latch is
refreshed.

### C2. Movement, `_go` delay, `STAY_ROTATE`

The person's position advance `FUN_14020260` (RVA `0x20260`,
`server/decompiled.c:23536-23588`) is **not** called once per server tick:
it is called for each *processed animation frame* of the animation state
machine `FUN_14021060` (RVA `0x21060`, lines 24517/24526). The state
machine advances animation frames with an ms cursor:

```
24283: iVar8 = param_1[0x18c]                  ; entity+0x630 = next-frame time (ms)
24287: uVar9 = param_1[0x157]                  ; entity+0x55c = frame delay (ms)
24288: iVar7 = DAT_14088e1c                    ; server now (ms)
24291: if ((uint)(iVar7 - iVar8) <= uVar9) return;   ; not due yet
24298: iVar8 = iVar8 + uVar9                   ; advance cursor by one frame
24299: param_1[0x18c] = iVar8
```

This is a `while` loop (`do { … } while(true)` from 24290): if the tick
arrives after more than one frame delay, all due frames are processed in
that tick. The unit is **ms**; the server tick only samples it. D-033's
raw ~63/~68 ms are the measured *inter-update delays* (from the frame
delay expression), not tick multiples. The wall-clock interval between
two updates is the next tick boundary at which the delay is due, i.e. a
boundary count times the effective period; at 35 Hz that quantization is
coarser than at 60 Hz (T5/T8).

Frame delay `entity+0x55c` is written from the selected animation header:

```
23470: *(uint *)(this + 0x55c) =
           *(int *)(DAT_1407fb90 + 0x8c) + -0x11 + (uint)*puVar5;
```

`DAT_1407fb90` is `gv_anim_speed` (registered at line 2789, default `0`),
`puVar5` is the animation descriptor selected from the pointer array at
`entity+0x170` and stored as the current descriptor at `entity+0x16c`;
`puVar5[0]` is the per-frame delay word and `puVar5[1]` is stored to
`entity+0x5ac` at line 23469 (frame count, read at 24316/24322/…). With
`gv_anim_speed = 0` the delay is
`anim_delay - 17` ms, i.e. the observed 80→63 and 85→68 ms. This makes the
D-033 `*0.8` factor a numeric coincidence of the fixed `-17` ms offset,
not a rate multiplier; the exact expression is additive in ms.

`STAY_ROTATE` (route type 1, parsed by `FUN_1401f9bc` RVA `0x1f9bc`,
`STAY_ROTATE` at line 22833) is chosen in `FUN_1401c93c` (RVA `0x1c93c`,
lines 20749-20763): `rand(10,25)` (line 20759) and `SET_DIRECTION` (state
`0x10`) are scheduled. `SET_DIRECTION` sets the turn frame delay to
`(+0x55c/3)*2` ms (`FUN_14021bc8` RVA `0x21bc8`, lines 24958-24970), i.e.
2/3 of the normal frame delay. The action is followed by the shared pause
gate. The port's fixed 500 ms rotate pause (D-035) is a port limiter, not
an original constant.

## Impact matrix

The original has no single "35 Hz tick count" for an arbitrary time span. The
only safe oracle is a frame schedule plus the 28 ms gate:

```
last_ms = 0
for each host frame sampled at integer clock t_ms:
    if t_ms - last_ms >= 28:
        run exactly one server tick
        last_ms = t_ms
```

There is no accumulator, no `while` catch-up and no max-frame clamp. For a
constant frame time `F`, the ideal period is `F * ceil(28 / F)` for `F < 28 ms`
and `F` for `F >= 28 ms` (T5). The counts below use `F = 28 ms` unless a row
says otherwise. Every test that uses a different `F` must state that `F` and
must not be "fixed" by copying the port's new output.

If a test keeps the current `advance(1/60)` frame grid, `F = 16.667 ms` gives a
`16.667 * ceil(28/16.667) = 33.33 ms` period, i.e. about **300 ticks per 10 s**
(not 357 at 28 ms and not 600 at 60 Hz). Changing only the loop bound is
therefore insufficient; the frame grid itself must be replaced or declared
(OQ-T4-1).

Method labels: **A** = analytic from T3/T5/C2/C3; **R** = independent
integer-ms reference replay (scratch script in `%TEMP%`, same RNG seed);
**L** = read-only live original capture. Golden values that depend on RNG use
**R** first and **L** only to validate the reference.

## Verdict / decomposition

**Verdict: `implementable` (scoped).** The original tick gate is fully
pinned by static evidence: signed integer `trunc(1000 / sv_fps)` (28 ms at
35), evaluated once per host frame, with at most one server tick per frame,
no accumulator, no catch-up and no max-frame clamp (T3/T5). The core
scheduler and the ms-based consumers (C2-C5) can be implemented without
guessing constants. The scope qualifier is the host-frame abstraction: the
live host frame time `F` (U1) is not measured, so the exact effective wall
period is `F*ceil(28/F)` for `F < 28` and `F` for `F >= 28`; the port must
choose and document a frame grid (P2-9a, OQ-T4-1). Pause interaction
(OQ-T4-3), command dispatch per frame vs per tick, AI/restock cadence
(U-C5/U-C2) and animation-word identity (U-C1) remain explicitly scoped or
left ms-based; none blocks the core gate.

### Original model vs current port model

| Aspect | Original (proven) | Current port |
|---|---|---|
| Rate | threshold `trunc(1000 / sv_fps)` = **28 ms** at 35; not 28.571, not 60 | fixed `kFixedDt = 1/60` |
| Gate | `now_ms - last_ms >= 28`; one tick per host frame; `last_ms = tick-start now_ms` | accumulator `while (acc >= 1/60 && steps < 15)` |
| Catch-up | none; `F >= 28` slows the world to `F` | up to 15 steps, `kMaxFrameDt = 0.25`, accumulator reset |
| Time | absolute QPC-derived integer ms latched per executed tick (`DAT_14088e1c`) | `tick_index * 1000 / 60` |
| `sv_fps == 0` | gate skipped, tick every frame | n/a |
| Consumers | ms deadlines/accumulators; only sampling changes | ms formulas, but sampled at 60 Hz |
| `sv_game_speed` | additive ms bias to animation delay; live 0 | port `0.8` delay approximation |

Exact effective period: `F*ceil(28/F)` for `F < 28 ms`, `F` for `F >= 28 ms`
(floor-ms sampling ±1 ms); exactly 28 ms (35.714 Hz) only when the frame
grid lands on 28. The original does **not** run at a continuous 35.0 Hz.

### P2-9a - core tick (`ServerCore` + `LevelSimulation` step)

Representation:

- Expose an integer-ms frame entry, e.g. `tick_frame(std::int64_t now_ms)`
  (preferred; OQ-T4-1), or keep `tick(dt)` only as a wrapper that produces
  an explicit frame grid. Store `sv_fps` (default 35 from config) and
  `tick_interval_ms = 1000 / sv_fps` using truncating integer division; do
  not add a `35.0` or `28.571` constant.
- Per frame: if `sv_fps != 0` and `now_ms - last_tick_ms < tick_interval_ms`,
  do not tick. Otherwise run exactly one server tick, `++tick_index`,
  latch `simulation_time_ms = now_ms`, and set `last_tick_ms = now_ms`.
  `sv_fps == 0` skips the gate (tick every frame).
- Delete the accumulator, `kFixedDt`, `kMaxFrameDt`, the
  `kMaxStepsPerTick` catch-up loop and the accumulator reset. Keep
  invalid-dt rejection only in the compatibility wrapper.
- `LevelSimulation::advance` receives the actual executed-tick delta
  (`now_ms - previous_simulation_time_ms`, integer ms -> seconds) and runs
  one pass; `time_ms_` is the latched integer clock. Remove
  `time_ms_exact_`/`accumulator_`/`kFixedStep`. This one-pass-per-tick
