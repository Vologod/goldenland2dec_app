## 1. Условные модификаторы (time-of-day) — реализуемо

### 1.1 Применимость — `FUN_12020e68` (RVA `0x20e68`)

`__thiscall int(this=wrapper, const Modifier*)`, где запись
`{+0 id, +4 int value, +8 uint flags, +0xc uint cond, +0x10 extra}`:
```
if flags & 0x2  and this+0x3c != DAT_12123f28 (1.0f)  -> reject
if flags & 0x4  and this+0x3c != DAT_12123f24 (0.0f)  -> reject
if flags & 0x8  -> interval check against this+0x2c (hour) and this+0x30 (tick)
                   startHour=(cond>>8)&0xf, startTick=cond&0xf
                   endHour=(cond>>24)&0xf, endTick=(cond>>16)&0xf
                   require [startHour,startTick] <= (hour,tick) <= [endHour,endTick]
if flags & 0x200 -> reject
else accept
```
Константы `.data1` (objdump `-s`): `0x12123f24 = 0.0f`,
`0x12123f28 = 1.0f`; `0x12123f20 = 0.9f` (не участвует).

`this+0x3c` — **фактор день/ночь** (0..1). Источник: `FUN_120b3160`
(RVA `0xb3160`):
```
clock+0x18(wrapper+0x1c)              // hour snapshot
wrapper+0x3c = clock+0xc              // day/night factor
```
`clock` = `DAT_12110ef8` (ctor `FUN_120b017c`, vtable `PTR_LAB_121311d0`);
слот `+0xc` = RVA `0xafcac` (дизасм):
```
hour = clock+0x20
hour < 7 or hour >= 22 -> 0.0f
8 <= hour < 21         -> 1.0f
hour == 12             -> 1.0f
hour == 7  (sunrise)   -> (min + sec/60) / 60
hour == 21 (sunset)    -> 1 - (min + sec/60) / 60
```
Это ровно `gl::game::day_night_factor(GameDatetime)` (D-104/P6a9b).

`FUN_120b3160(DAT_12110efc)` вызывается при входе на экраны `0xd/0xe/0xf`
(`FUN_1203c7f0/c6a4/c564`, диспетчер `FUN_1203c2xx`); значит при открытии
крупных игровых экранов (в т.ч. листа) фактор день/ночь синхронизируется с
текущим временем. Порт вычисляет `day_night_factor(calendar_.now())` в
момент открытия листа — эквивалентно.

Проверка equality — побитовая по `float`: значение `1.0` только в
8..20 ч, `0.0` только при hour<7 или >=22; на рассвете/закате (7/21)
фактор дробный и **не** совпадает ни с одним — модификатор неактивен.

### 1.2 Корпус ITM — какие условные биты реально используются

Все 1 848 ITM / 2 142 effect разобраны (парсер = `src/assets/src/itm.cpp`).
Гистограмма `effect.flags`: `0x01(3) 0x41(1609) 0x42(30) 0x44(57)
0x50(82) 0x60(5) 0x81(338) 0x82(3) 0x84(9) 0x90(6)`.

- Условные биты: `0x2` (день) — 33 effect, `0x4` (ночь) — 66 effect.
- `0x8` (интервал) и `0x200` (reject) — **0** в шипнутых данных.
- Комбинации: `0x42/0x82` = flat/percent + «день», `0x44/0x84` =
  flat/percent + «ночь».
- 31 предмет использует условные эффекты: типы 0 sword (4), 1 axe (1),
  7 blunt (8), 11 helmet (1), 12 armor (2), 13 shield (1), 14 elbarms (2),
  15 bracelet (4), 16 amulet (1), 17 ring (5), + type 15 items 5/16/35/…;
  полный список id: 5,16,35,76,89,173,213,216,225,239,276,326,327,342,
  389,394,463,540,568,571,575,588,605,835,867,872,873,879,884,891,896.
- Условные effect-типы — атрибуты/боевые (`6,7,8,9,10,11,13,15,16,17,
  22,23,25,26,28,29,44,51`); **нет** типов `0/1/2` (стихийные моды оружия),
  поэтому стихийный урон (см. §5) условий не касается.

### 1.3 Slot0 не затронут

Экипировка slot0: `72,397,280,318,80,233,554,141,486,353,245` — ни у
одного предмета нет условных эффектов (`cond=0`). Оракул листа
(`armor=15, weight=132/204.6, AP=43, crit=7, acc=90, …`) не меняется.

## 2. Режимные флаги — дефолты подтверждены

Регистрация конфига — `FUN_120022d4` (RVA `0x22d4`), getter `+0x10(name,
default, flags)`. В шипнутом `GoldenLand.ini` этих ключей **нет** → порт
обязан брать дефолты:

| `DAT_` | ключ | default | смысл |
|---|---|---|---|
| `DAT_12106bc0` | `gv_addon` (адрес `0x1212251b+1`) | `0` | addon/cheat-режим |
| `DAT_12106ab8` | `ch_KrepkajaSpina` | `0` | перк «Крепкая спина» |
| `DAT_12106abc` | `ch_ZorkijGlaz` | `0` | перк «Зоркий глаз» |
| `DAT_12106ac4` | `ch_max_skill_value` | `0xf` = 15 | кап навыков |
| `DAT_12106ac0` | `ch_max_primary_value` | `0x1e` = 30 | кап атрибутов |

Следствия при дефолтах (что и реализовано):
- `gv_addon=0` → у брони множитель `1.35` **не** применяется
  (`FUN_1201f7a0`), а множитель веса `1.1` при `this+0xf8&0x2000`
  **применяется** (`FUN_1201e92c`); текущий вес не форсируется в 13.
- `ch_KrepkajaSpina=0` → `Вес cur` = реальная сумма, не `13`.
- Капы 30/15 — уже реализованы (`kMaxPrimaryValue`, `combat_stats.cpp`).
- `gv_addon!=0` меняет и другие вещи (стартовая локация `volcano_1`,
  step delay и т.п.) — вне scope листа.

Вердикт: для шипнутой игры режимные флаги = 0; формулы порта корректны.
Опциональное чтение этих ключей из ini не требуется (ключей нет).

## 3. Бонусные поля `this+0x16c..0x184` и бонусные навыки `this+0x198`

- Геттеры атрибутов (`FUN_12020620/205b8/204e8/20550/20468/20380/20400`)
  = `round(FUN_1201b1c4(recordField, statId))` **+** бонус-поле
  (`0x16c/0x170/0x174/0x178/0x17c/0x180/0x184`) **только если**
  `this+0xc != 0`.
- Бонус навыка: `FUN_1201fab4` = `recordSkill[+0x7c+4*id]` +
  `bonusSkill[+0x198+4*id]` при `this+0xc != 0`, clamp `0..15`.
- `this+0xc` инициализируется **1** (`FUN_120b3784`, RVA `0xb3784`,
  `param_1[3]=1`); бонусные массивы обнуляются в `FUN_1202078c` и при
  входе на экраны `0xe/0xf` (`FUN_1203d…`, строки 46648+).
- Бонусные поля заполняются **распределением очков атрибутов при
  повышении уровня** (`FUN_1201e154/df18/dcdc/daa0/d864/d628/d3ec`,
  RVA `0x1e154..0x1d3ec`: «±1 атрибут», пул очков `+0x194`,
  доступно `+0x74`) и временными баффами. В свежем сейве они = 0, а
  распределённые при levелапе очки либо остаются в бонусных полях, либо
  коммитятся в базовую запись (точный момент коммита не снят).

Вердикт: для листа, открытого на загруженном сейве вне окна
распределения очков, бонусные поля = 0, поэтому порт (без levелап-UI)
совпадает. Полная модель требует подсистемы повышения уровня/баффов —
отдельная задача (P5-runtime), не residual формул листа. Порт уже
корректен для случая «bonus = 0».

## 3.1 Активные эффекты магии/зелий/еды/заданий/проклятий/травм — отдельный канал

Временные эффекты (заклинания, зелья, еда, травмы, а также эффекты,
налагаемые квестами и проклятиями) в оригинале **не** идут через
бонусные поля §3, а попадают в общий список эффектов персоны и далее в
тот же контейнер модификаторов, что и экипировка.

**Список эффектов персоны (Server.dll).** Запись — 5 слов (`0x14` байт)
`{+0 type/id, +4 value, +8 flags, +0xc cond/time, +0x10 extra}` — ровно
формат ITM-эффекта/модификатора:
- данные `person+0x110C`, count `person+0x14F4`, capacity `+0x14F8`
  (`FUN_14018848`, `FUN_1401798c`, `FUN_1401d99c`);
- сериализуется в сетевой пакет персоны `FUN_1401d84c` (RVA `0x1d84c`:
  `writer(person+0x110C, count*0x14)`) и читается обратно
  `FUN_1401d8bc` (RVA `0x1d8bc`);
- потиковое старение (`RVA 0x57954`): `flags&0x10` — длительность
  (`cond`, часы/минуты), `flags&0x20` — задержка; по истечении запись
  удаляется. Поэтому один и тот же список несёт и мгновенные, и
  отложенные, и временные эффекты.

**Клиент.** При rebind персоны `FUN_1201b034` вызывает
`FUN_120b0278` (пересборка из экипировки) и `FUN_120b0690` (RVA
`0xb0690`, wrapper vtable `+0x10`), которая перебирает глобальный
активный список локального игрока `DAT_12110f28+0x6DC` (count `+0x6E0`)
и добавляет его записи в контейнер `wrapper+0x40`. Записи с
`flags&0x20` и ненулевым младшим 16-бит `cond` (ещё не наступившая
задержка) пропускаются. `FUN_120b31c8` (RVA `0xb31c8`) заменяет список
и пересобирает контейнер (vtable `+0xc`/`+0x10`).

Следствие: `FUN_1201b1c4` (и все геттеры листа) применяет **все** такие
эффекты одинаково (flat `0x40`, percent `0x80`, override, условия
`0x2/0x4/0x8/0x200`), поэтому они видны в листе и во всех производных
значениях (броня, вес, AP, крит, точность, сопротивления, урон).

**Проклятые предметы** — это обычные ITM-эффекты; конфиг `cc_cursed` —
только цвет иконки. Их стат-моды идут через экипировку и уже
применяются портом при надевании.

**Квестовые `LE_*` (Server.dll).** `LE_CastEffect`/`LE_DelEffect`
(`FUN_140347e4`/`FUN_140348dc`) создают/удаляют **именованные
эффект-сущности уровня** (менеджер `level+0x2564/0x2568/0x256c`, тип
`(flags&0x3e)==4`, активность `+0x1A4`, имя `+0x4c`), а не
стат-модификаторы персоны. `LE_CastMagic` (`FUN_14034228`) запускает
магию и может порождать эффекты персоны (см. выше). Т.е. квестовый
скрипт, который меняет статы героя, делает это либо через эффект
персоны (`LE_CastMagic`/аналог), либо напрямую
`RS_SetPersonParameterI` (пишет в запись персоны — порт это читает).

**В порте:** `PersonState.effects` (`PersonEffect` = 5 слов) уже
существует, но заполняется только записью травмы `RS_SetInjured` и **не
передаётся** в `combat_stats`; `LE_CastEffect`/`LE_CastMagic`/магия/
потребление зелий/еды не реализованы (unsupported natives). Поэтому
эффекты квестов/проклятий/магии/зелий/еды/травм в лист пока не
попадают, хотя формулы `FUN_1201b1c4`/`apply_modifiers` их примут, если
скормить записи (с учётом `flags&0x20` для ещё не наступившей задержки).
Это отдельный инкремент P5 (effect runtime), не правка брони/веса.

## 4. Активный набор A/B — не residual листа

`local_player+0x6E4` (0=A,1=B) — runtime UI-состояние инвентаря, не
сейвится; переключается клавишами (`FUN_120c7008`). Порт по решению
P5b1/P5c2 берёт A (`weapon 0x001000`, `shield 0x400000`). Моделирование
переключения набора — часть инвентарного UI (P5b), не формул листа.

## 5. Стихийный урон и условия

`FUN_1201edfc/ef98/f134` (стихийный урон) суммируют моды **оружия** с
`word0 == idx` напрямую и **не** вызывают `FUN_12020e68` — условия не
проверяются (и в корпусе нет стихийных условных модов). Значит
`elemental_damage` в порте оставляем без conditions (паритет).
