## 2. Лексика (лексер `FUN_14002af0`)

Парсер работает не построчно, а по **токенам**; переводы строк не значимы.

- Разделители — любые байты `<= 0x20` (пробел, TAB, CR, LF); они
  пропускаются (`decompiled.c:1812-1822`).
- Токен — непрерывная последовательность байтов `> 0x20`; длина токена
  ограничена `0x3ff` символами (`decompiled.c:1823-1830`), но вызывающие
  читают его в буфер `0x104` байт (`FUN_140034e0`, `decompiled.c:2399-2429`),
  т.е. фактический лимит значения — `0x103` символа.
- Комментарий — `//` до конца строки (`DAT_1408c600 = "//"`,
  file offset `0x80600`). Распознаётся:
  - в начале токена: токен, начинающийся с `//`, отбрасывается, остаток
    строки пропускается (`decompiled.c:1855-1867`);
  - внутри токена (attached): как только последние два записанных символа —
    `//`, остаток строки пропускается (`decompiled.c:1833-1842`), но сам
    токен **не завершается**: после перевода строки читается следующий
    байт, и если он `> 0x20`, запись продолжается в тот же буфер
    (`0x14002b80`–`0x14002bf7`: `jg 0x14002b3c`, индекс токена `ebp` не
    сбрасывается). Поэтому `5//comment` даёт токен вида `5//item`
    (или `5//`), а не `5`; `get_double` его отвергает. Эквивалентности с
    `5   //comment` нет.
- В реальном корпусе 586 trailing-комментариев (`//` после значения), все
  отделены от значения пробелом; attached (`5//comment`) — 0 (см. §5.1).
- Блочных комментариев `/* ... */` лексер не поддерживает; в корпусе
  238/238 файлов нет ни одного `/*`.
- Ключи сравниваются ASCII case-insensitive: `FUN_14074260` приводит
  `A`–`Z` к нижнему регистру (`decompiled.c:82875-82893`). В реальных
  данных все ключи в нижнем регистре.
- Двоеточий/иных разделителей нет: ключ и значение — отдельные токены.
  В корпусе токенов с `:` нет.
- Строки — только в двойных кавычках (`FUN_14002cac` требует `0x22`,
  `decompiled.c:1904-1907`); перед кавычкой допускаются `//`-комментарии.
- Кодировка данных — ASCII/cp1251; в корпусе 238/238 файлов только байты
  `<= 0x7f`, CRLF, без BOM и NUL.

### 2.1 Числа

- `double`-токен (`FUN_140031b8`, `decompiled.c:2185-2198`) валиден, только
  если все символы — `0`–`9`, `+`, `-` или `.`; далее вызывается
  `FUN_1406b50b` (atoi/atof-подобный разбор). Пустой/иной токен → `-3`,
  значение не применяется.
- `int`-токен (`FUN_14003390`, `decompiled.c:2342-2392`) принимает
  десятичные цифры и `-` в **любой** позиции (валидатор, 2371-2376),
  либо `0x`/`0X` + hex-цифры (`FUN_14002f54`); `+` не допускается.
  Разбор значения — `FUN_1406b3e9` (atoi-подобный). Реальные счётчики —
  обычные неотрицательные decimal.

## 3. Грамматика `.inv`

```
file            := { key_decl | special_decl | item_decl | comment | junk_token }
key_decl        := key ws number
key             := "regenerate_chance" | "chance_decrease"
                 | "quantity_decrease" | "level_offset"
special_decl    := "special" ws token
item_decl       := "item" ws quoted_name ws n1 ws n2 ws n3 ws n4 ws n5
quoted_name     := '"' ... '"'
n1,n2,n3        := number          ; double-токен
n4,n5           := integer         ; int-токен
```

`ws` — любые байты `<= 0x20` (включая переводы строк), т.е. токены могут
быть разнесены по строкам.

Правила разбора (`FUN_14047784`, `decompiled.c:48693-48965`):

1. Файл открывается как memory-mapped (`FUN_14003538`, 48695).
2. **Четыре независимых полных прохода** по файлу: для
   `level_offset`, `regenerate_chance`, `chance_decrease`,
   `quantity_decrease`. Header-rewind'ы — `FUN_14003600` на 48772, 48784,
   48796; rewind на 48802 относится уже к проходу `special`, а 48841 — к
   проходу `item`. Поэтому порядок заголовков в файле произволен;
   сохраняется **первое валидное** вхождение ключа (`break` после
   успешного чтения); отсутствующий или битый ключ оставляет значение из
   clear.
3. Полный проход по `special` (48805-48840), значения добавляются в
   список в порядке файла.
4. Полный проход по `item` (48844-48942), записи добавляются в массив в
   порядке файла.
5. Закрытие файла и **безусловный сброс** списка `special` (см. §5.3).

Заголовки и значения:

| Ключ | Запись в память | Default (clear) | Смысл |
|---|---|---|---|
| `regenerate_chance` | `+0x40 = (float)(value * 0.01)` (48778) | `1.0f` | вероятность регенерации, проценты |
| `chance_decrease` | `+0x38 = (float)value` (48790) | `1.0f` | множитель/шаг уменьшения шанса |
| `quantity_decrease` | `+0x3c = (float)value` (48969) | `1.0f` | множитель/шаг уменьшения количества |
| `level_offset` | `+0x44 = (float)value` (48766) | `0.0f` | сдвиг уровня для окна предметов |

Default-значения задаёт `FUN_140471cc` (`decompiled.c:48322-48327`):
`+0x38/+0x3c/+0x40 = 0x3f800000` (1.0f), `+0x44 = 0`. Вызывающие
(`FUN_1404805c` 49017/49022, 49488/49494, 49875/49902, 51120/51126)
сначала вызывают clear, затем парсер: `FUN_14047784` сам объект не
очищает.

Строка `item` (порядок токенов и поля записи):

| Токен | Значение | Поле записи (`0x18` stride) |
|---|---|---|
| `item` | ключевое слово | — |
| `"TECH"` | имя предмета (строка в кавычках) | `+0x00` `char*` (копия через alloc+memcpy) |
| `n1` | double | `+0x10` `int32` = `(int)n1` |
| `n2` | double | `+0x14` `int32` = `(int)n2` |
| `n3` | double | `+0x04` `float` = `(float)n3` |
| `n4` | int | `+0x08` `int32` = `n4` |
| `n5` | int | `+0x0C` `int32` = `n5` |

Запись 24 байта (`0x18`); поля заполняются в
`decompiled.c:48855-48868` (новая запись) и `48903-48915` (append).
Ассемблерные сохранения: `+0x04` `0x14047d29`, `+0x10` `0x14047d58`,
`+0x14` `0x14047d79`, `+0x08` `0x14047d82`, `+0x0C` `0x14047d91`
(для append — `0x14047e4d`…`0x14047ee1`).

Все пять числовых токенов **обязательны**: после каждого чтения стоит
`test eax,eax; jne 0x14047f4a` (skip record); проверка — ассемблер
`0x14047c76`, `0x14047c90`, `0x14047cb6`, `0x14047ccd`, `0x14047ce4`.
Если хотя бы одно чтение не удалось, запись не создаётся, а неудавшийся
токен «возвращается» (`FUN_14003310`) и читается следующим циклом
(`0x14047f4a` → re-check на `0x14047c22`).

`n1`/`n2` приводятся к int через FPU `fistp` с принудительным
rounding-control `0xC00` (truncate toward zero), а не rounding-to-nearest:
ассемблер `0x14047d3b`–`0x14047d70` и `0x14047e5f`–`0x14047eb3`; Ghidra
показывает это как `ROUND`. В реальных данных все `n1`/`n2` целые, так
что разницы нет.

## 4. In-memory layout

Объект «шаблон инвентаря» (`this` в `FUN_14047784`):

| Смещение | Тип | Поле | Default после clear |
|---|---|---|---|
| `+0x38` | float | `chance_decrease` | `1.0f` |
| `+0x3c` | float | `quantity_decrease` | `1.0f` |
| `+0x40` | float | `regenerate_chance` (0..1) | `1.0f` |
| `+0x44` | float | `level_offset` | `0.0f` |
| `+0x48` | int32 | special count | `0`; после успешного parse — `0x3a` |
| `+0x4c` | int32* | special array | `null`; после parse — `[0..57]` |
| `+0x50` | record* | item array (`0x18` stride) | `null` |
| `+0x54` | int32 | item count | `0` |
| `+0x58` | char[] | кэш имени загруженного файла (NUL-terminated) | первый байт `0` |

Clear: `FUN_140471cc` (`decompiled.c:48287-48329`) освобождает `+0x4c`
(48295-48298) и массив записей `+0x50` с их name-строками
(48299-48321), затем ставит defaults (48322-48327). Длина буфера
`+0x58` в декомпиле не видна (clear пишет только `[0] = 0`,
`decompiled.c:48324`); загрузчики копируют туда полный путь без видимой
проверки границы (`decompiled.c:49027-49032` и 49467-49507) — точный
размер `unverified`.

### 4.1 Item array (`+0x50`/`+0x54`)

- Первая запись: `count == 0`, `count = 1`, `alloc(0x18)` (`48855-48859`).
- Каждая следующая: `alloc(count*0x18 + 0x18)`, `memcpy` старых
  `count*0x18` байт, `free` старого массива, запись в конец,
  `count += 1` (`48887-48935`). Порядок записей = порядок `item` в файле.
- Поля записи — таблица §3. Строка имени копируется `strlen+1`
  (`48870-48885`).

### 4.2 Special list (`+0x48`/`+0x4c`)

- `special` читает **один plain-токен** (`FUN_140032e4`, 48807), не
  обязательно в кавычках, и передаёт его в
  `(*(*DAT_14088df4 + 0x14))(&token, &value)` (48810; ассемблер
  `0x14047b25`/`0x14047b4c`). При успехе `value` добавляется в массив
  `+0x4c` (append, как у item, 48813-48835; ассемблер `0x14047bd2`).
- После прохода item массив `special` **безусловно** освобождается и
  заменяется на identity: `+0x48 = 0x3a` (58), `+0x4c = alloc(0xe8)`,
  `+0x4c[i] = i` для `i = 0..57` (`decompiled.c:48943-48961`;
  ассемблер `0x14047f7f`–`0x14047fdf`).
- Следствие: после любого успешного parse локальный список special
  всегда `[0..57]`; значения из файла в объекте не сохраняются.
  Возможный глобальный побочный эффект вызова vtable `+0x14` не
  проверялся (`unverified`); в реальном корпусе активных `special` нет.

### 4.3 Семантика полей (для Task 2)

Значение полей подтверждается генератором `FUN_140489ec` (его разбор —
Task 2), см. `decompiled.c:49517-49545`:

- `level = *(int*)(DAT_14088dc4 + 0x26c4) + 1` (49517);
- запись участвует, если
  `rec+0x10 + this+0x44 <= level <= rec+0x14 + this+0x44`
  (49526-49527), т.е. `n1`/`n2` — относительное окно уровней;
- шанс: `FUN_14006288(_DAT_14091e30 * rec+0x04)` (49528), где
  `_DAT_14091e30` = `double 0.01`, т.е. `n3` — проценты; если
  `n3 == _DAT_14091e44` (`0.0f`), запись пропускается без ролла
  количества (`49534-49536`);
- количество: `FUN_140061e4(rec+0x08, rec+0x0C)` (49538-49539), т.е.
  `n4`/`n5` — min/max count.

## 6. Unverified / open questions

1. **4-числовые `item` (362 строки).** Статически код требует 5 чисел и
   молча пропускает такие записи; намеренно ли это в данных и совпадает
   ли с live-поведением оригинальной игры — не проверено live.
2. **`special`.** Тип значения (plain-токен → `DAT_14088df4` vtable+0x14)
   и смысл результата не установлены; активных `special` в корпусе нет.
   Локальный список после parse всегда перезаписывается identity
   `[0..57]`; возможный глобальный side effect вызова vtable не проверен.
3. **`+0x58`.** Точный размер буфера кэша имени файла в декомпиле не
   виден (clear пишет только `[0]`) — `unverified`.
4. **Truncation vs rounding для `n1`/`n2`.** Код использует FPU truncation
   (`fistp`, RC=`0xC00`); в реальных данных значения целые, поэтому
   наблюдаемой разницы нет.
5. **Дубликаты ключей.** Статически побеждает первое валидное вхождение,
   но в корпусе дубликатов нет — сценарий не упражнялся.
6. **`special`/`item` порядок.** Записи добавляются в порядке файла;
   interleaving `item`/`special` в данных отсутствует, но код сканирует
   их отдельными проходами (сначала все `special`, затем все `item`).
7. **`/* */`.** Не поддерживаются лексером и не встречаются в данных.
8. **Live-оракул не снимался.** Все выводы — статический дизассемблер +
   реальные файлы; память запущенной игры в этой задаче не читалась.

### 8.2 Существенные свойства

- **Выбора случайной записи нет.** Записи перебираются строго в порядке
  файла (`this+0x50`, stride `0x18`); рандом решает только «попадание»
  каждой записи, количество и specials.
- `regenerate_chance` в `FUN_140489ec` **роллится, но на генерацию не
  влияет**: `box` всегда новый и пустой, поэтому
  `FUN_14030f98(box+8) == 0` и ветка «оставить» не срабатывает. Ролл
  всё равно потребляет один `rand()` и важен для последовательности.
  В `FUN_1404805c`/`FUN_1404b1c0`, где контейнер может быть непустым,
  этот ролл уже значим (§10.2).
- **Ранний выход**: как только в контейнере набралось `>= 4` стеков
  (`cnt >= 4`, asm `0x14048cf7` `cmp eax,4; jae`), генерация
  прекращается, контейнер регистрируется в пуле менеджера
  (`+0x15c`/`+0x160`/`+0x164`/`+0x168`) по первому свободному биту и
  возвращается. Если записей не хватило — возвращается контейнер с
  меньшим числом стеков.
- **Отдельного money-ролла нет.** В `.inv` нет денежного поля, и в
  `FUN_140489ec` нет отдельной ветки денег/золота. При этом `.inv`-записи
  `MON_*` — обычные предметы: они создаются тем же путём
  `FUN_1404e3a4`/`FUN_1404dbec` и попадают в контейнер как стеки; валюта
  в порте — это те же инстансы `MON_*` (см. §11).
- Ветка `if (rec.n3 == 0.0f) skip` (`decompiled.c:49534-49536`)
  недостижима в нормальном потоке: при `n3 == 0` вызов
  `FUN_14006288(0.0)` уже вернул 0, и запись пропущена раньше.
  Это защитный дубль; на реальных данных не упражняется.

## 9. RNG: источник, семантика, полный список вызовов

### 9.1 Источник и seed

- `_rand` — `FUN_1406c09f` (RVA `0x6c09f`, `decompiled.c:73211-73228`),
  библиотечная функция MSVC CRT (VS2003/2005/2008):
  `state = state*0x343FD + 0x269EC3; return (state >> 16) & 0x7FFF`.
- Seed задаётся один раз: `FUN_1406c092(timeGetTime())` в
  `FUN_1402fdc0` (RVA `0x2fdc0`, `decompiled.c:34129`). Это `srand`;
  других вызовов `FUN_1406c092` в корпусе нет. Значит **единый общий
  MSVC-поток**, инициализируемый `timeGetTime()`; отдельного RNG для
  лута нет. Точный триггер/время вызова `FUN_1402fdc0` (инициализация
  мира, загрузка сессии или иное) — `unverified`: callers в корпусе 0.
- Следствие: чтобы точно воспроизвести лут, порту нужен либо тот же
  seed (+ вся предшествующая выборка из общего потока), либо
  инъекция seed в детерминированном тесте.
- **Конфликт с D-030 (`docs/DECISIONS.md:37`).** D-030 утверждает, что
  в `Server.dll` нет `srand` (seed 1) и что `range()` округляет к
  ближайшему. Оба утверждения опровергнуты: `srand` есть
  (`FUN_1406c092(timeGetTime())`, `decompiled.c:34129`), а
  `FUN_140061e4` усекает (§9.3). Это не лут-специфичные функции:
  движение вызывает `FUN_140061e4(-r,r)` в `FUN_1401c2a0`
  (`decompiled.c:20410-20411`), лут — `:49538`. D-030 исправлена
  записью **D-053** (seed + truncation); seed=1 — документированное
  отклонение, а не паритет. Follow-up — `docs/STATUS.md` (Phase 1b2b2a)
  и D-053.

### 9.2 `FUN_14006288` — вероятность (RVA `0x6288`)

`decompiled.c:4385-4400`, asm `0x14006288-0x140062dc`.

```

    if p <= 0.0f:        return 0
    if p >  1.0f:        return 1
```

Константы: `0x1408d7cc=0.0f`, `0x1408d7c8=1.0f`, `0x1408d7c4=1/32767`

Гейт `DAT_14088dc4+0x26c0` связан с `BT_RGINF`

- `decompiled.c:35812-35814` читает `BT_RGINF` и кладёт сырое значение

- `decompiled.c:35817-35842`: если `+0x26c0 == 0`, выполняется сравнение

обнуляет `+0x26c4` при инициализации (`decompiled.c:33982`) и там же

  `unverified`.
- **stacking в `FUN_1404e3a4`.** Merge-путь увеличивает существующий
  стек на 1 (`decompiled.c:53793`) и возвращает его (`53809`)
  независимо от `chunk`; полное условие входа в merge-путь не
  доказано.
- **live-оракул не снимался.** Нет 0/N сверки контейнеров при

   подтверждает отсутствие net-бонуса на момент save.
6. **Следствие для порта.** При загрузке save сохранённое значение —
   авторитетно: reader ставит поле (`35637-35638`), затем
   `FUN_140325fc` (`35640`) читает BT_ENTS (`35847-35915`) и создаёт
   сущности — т.е. поле установлено до их создания (live-порядок не
   снимался, `unverified`).
   На новом старте поле `0` (init) до первого world update, поэтому
   первый уровень грузится с loot level `1`. В идущей сессии —
   текущий party level (`FUN_140254bc`). Для одиночного героя
   `party_level = FUN_1400cbc0(EXP) + (Scout>9 ? 5 : 0) +
   (Identify>4 ? 5 : 0)`; в порте допустимо брать `+0x26c4` из save,
   а при его отсутствии — `0` (new game) или runtime-значение.

#### Контейнер save и точные смещения `BT_INFO`

- Файл save: 104-байтный header (`0x00-0x67`), затем
  `u32 uncompressed_size` (`0x68`), `u32 compressed_size` (`0x6C`),
  zlib-поток с `0x70` (`112`). `decode_save_body` порта (header `112`)
  корректен: `0x68 + 8 = 0x70`.
- Разжатый payload — конкатенация блоков
  `[8-byte tag][u32 size][payload]`.
- Тег `BT_INFO ` = `42 54 5F 49 4E 46 4F 20`. Во всех 28 save он лежит
  по decompressed offset `0xB71C4` (потому что `BT_SCRN` всегда
  `0xB71B8`), но искать нужно по тегу, не по константе.
- Payload `BT_INFO` (reader `35628-35639`, writer `35386-35396`), строго
  по порядку:

| # | Поле | Размер | Смещение в payload |
|---|---|---|---:|---|
| 1 | username (`cl_username`; writer `35387` = `DAT_1407fcc8+4`) | u32 len + bytes | `0x00` |
| 2 | `+0x218` (режим мира; `0/1`) | u32 | после username |
| 3 | world-state blob (`DAT_14088e14` vtable `+0x18/+0x1c`) | `0x20` | после #2 |
| 4 | caption/title (reader отбрасывает, `35635`) | u32 len + bytes | после #3 |
| 5 | level name (`L93_4`, `L6_3`, …), идёт в `FUN_140325fc` | u32 len + bytes | после #4 |
| 6 | **`+0x26c4` (party level)** | u32 | после #5 |
| 7 | `+0x26c8/+0x26cc` (init `-1`; ushort на `30864`) | 8 bytes | после #6 |

Точное смещение поля в payload:
`4 + len(user) + 4 + 0x20 + (4 + len(caption)) + (4 + len(level))`.
Абсолютный decompressed offset = `tag + 12 + это смещение`.

| save | tag | size | payload | user len | caption len | level len | `+0x26c4` payload | abs | value | level |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|---|
| slot0 | `0xB71C4` | 100 | `0xB71D0` | 6 | 29 | 5 | `0x58` | `0xB7228` | **40** | `L93_4` |
| slot2 | `0xB71C4` | 86 | `0xB71D0` | 6 | 16 | 4 | `0x4A` | `0xB721A` | **36** | `L6_3` |
| slot21 | `0xB71C4` | 87 | `0xB71D0` | 6 | 17 | 4 | `0x4B` | `0xB721B` | **1** | `L1_1` |

Read-only алгоритм (без записи в save):

```
tag     = find("BT_INFO ")
size    = u32le(data, tag + 8)
p       = tag + 12
user    = string(p); p += 4 + len(user)
v218    = u32(p);    p += 4
blob    = data[p:p+0x20]; p += 0x20
caption = string(p); p += 4 + len(caption)
level   = string(p); p += 4 + len(level)
party_level = u32(p); p += 4
tail    = data[p:p+8]
```

`+0x218`, blob (`0x20`) и `+0x26c8/0x26cc` для лута не нужны; их
семантика — `unverified` (blob идёт в `DAT_14088e14`, не в RNG-поток).

#### `FUN_1404b1c0` — точная RNG/creation семантика (SEF NPC)

`FUN_1404b1c0` (RVA `0x4b1c0`) вызывается из SEF `scr_inv`
(`FUN_1401edc4` `22451-22455`) с `param_1 = +0xc` (hot),
`param_2 = +0x10` (main; его читают `TestPersonHasItem`/
`GetItemCountI`, `p3b2a` §2.1/§2.2/§4.3), `param_4 = 1`.
Оба контейнера очищаются (два `FUN_1404d724`; asm
`0x1404b35a`/`0x1404b362`). RNG — строго в порядке:

| # | Проход | Вызов | Аргумент | Где |
|---|---|---|---|---|
| R1 | до проходов, всегда | `coin` | `this+0x40` (`regenerate_chance`) | `51141`; asm `0x1404b328` |
| R2 | pass 1 | `coin` | `0.01 * n3` | `51161`; asm `0x1404b3f1-401` |
| R3 | pass 1 | `range` | `n4, n5` | `51171`; asm `0x1404b43f` |
| R4/R5 | pass 1 | `coin` | specials | `51191-51203`; **out of scope** |
| R2' | pass 2, только `n3 != 0` | `coin` | `(0.01*n3)/chance_decrease` | `51293`; asm `0x1404b6e7-6f8` |
| R3' | pass 2 | `range` | scaled `n4,n5` | `51313`; asm `0x1404b7e3` |
| R4/R5 | pass 2 | `coin` | specials | `51332-51358`; **out of scope** |

Pass 1 (`param_1` = `+0xc` hot):

- R1 всегда; при `R1=0 && param_4==0` — return без генерации; SEF
  `param_4=1` → генерация всегда.
- на запись в окне: R2; `n3==0` → skip; `R3 = range(n4,n5)`;
  `qty<1` → skip.
- creation loop: `this+4 = 1` — это **не** force-new: единственное
  чтение `DAT_14088df8+4` в `FUN_1404e3a4` очищает item-флаг `0x80`
  (`decompiled.c:53919-53921`), merge search не гейтит. Далее
  `FUN_1404e3a4(name,0,1)` (`decompiled.c:51177-51180`; asm
  `0x1404b45e-0x1404b46c`) → `item = FUN_1404dbec(id)` →
  `item+0xb0 = min(remaining, item+0x34)` (`51183-51187`; asm
  `0x1404b4c7-0x1404b4d9`) → `remaining -= min` (`51210`; asm
  `0x1404b4f4-0x1404b4fc`) → повтор, пока `remaining > 0`.
  Merge search общий для pass 1/2; pass-1 merge возможен и
  `unverified` (при merge счётчик затем перезаписывается `min`).
  Chunk-loop нет.
- метаданные (`+0x20`/`+0x1c=1`/`+0x24`/pool) только при
  `count >= 100000` (`0x186a0`; asm `0x1404b496`), т.е. практически
  недостижимы; **4-stack exit отсутствует**.

Pass 2 (`param_2` = `+0x10` main):

- окно то же; если `n3 == 0.0f` — chance coin **не бросается**
  (asm `0x1404b6e5: je 0x1404b716`), иначе R2'.
- qty: `scale = 1/quantity_decrease` (`0x1404b724-0x1404b732`);
  `n4*scale`, `n5*scale`; FPU trunc (RC=`0xC00`) + `+1.0`, если
  truncated != product (asm `0x1404b743-0x1404b7da`) → effective
  ceil for positive; затем `R3' = range(scaled_min, scaled_max)`.
- деление на `chance_decrease`/`quantity_decrease` не защищено.
  В реальном корпусе нулей нет (`chance_decrease` ∈
  {0.001,1,2,5,10,50,100}, `quantity_decrease` ∈ {1,3,10}, §5.1);
  поведение при 0 — `unverified`, зафиксировать в D-055 (Task 5).
- creation: `this+4 = 0` (item-флаг `0x80` сохраняется; merge search
  от него не зависит) → `FUN_1404e3a4(name,0,1)`
  (`0x1404b7fb-0x1404b80c`) → `item+0xb0 = min(remaining,
  item+0x34)` (`0x1404b857-0x1404b860`) → `remaining -= min`
  (`0x1404b881-0x1404b885`). Pass-2 merge возможен и полностью не
  трассирован (`unverified`).
- метаданные при `count >= 100000` (`0x1404b829`), `+0x1c = 0`
  (`0x1404b8a2`); 4-stack exit нет.

R1 не отменяет генерацию при `param_4=1`, но R1 всё равно
потребляется.

#### Shared `FUN_1404e3a4` merge и caller-квирки `FUN_140489ec`

Merge/stacking `+1` — в **shared** `FUN_1404e3a4`
(asm `0x1404e81c-0x1404e81f`; `decompiled.c:53790-53810`): при
существующем инстансе того же прототипа, `max_stack>=2`,
`current<max` — `+1` и возврат id. Это доступно и `FUN_1404b1c0`
(pass 1/2 merge — `unverified`).

Только caller-квирки `FUN_140489ec` (RVA `0x489ec`,
`decompiled.c:49416-49667`; hero/иной путь, **не** SEF NPC):

- вычитание из `qty` всего `chunk` (`49585`; asm
  `0x14048d48: subl %esi,%edi`), поэтому при `chunk>1` merge теряет
  `chunk-1` предметов;
- early exit при `>=4` стеках (asm `0x14048cf7: cmpl $0x4,%eax; jae`)
  с restock-метаданными `+0x20`/`+0x1c=1`/`+0x24`.

К `FUN_1404b1c0` эти caller-квирки **не** применять.

### 15.3 Порядок RNG на спавне (доказано/расхождение)

**Доказано:**

- SEF-спавн: `FUN_1401edc4` (RVA `0x1edc4`) парсит `persons:` в порядке
  файла (ключи `position`, `literary_name`, `direction`, `route_type`,
  `route`, `radius`, `delay_min`, `delay_max`, `tribe`, `scr_dialog`,
  `scr_inv`; `decompiled.c:22102-22722`). На `scr_inv`
  (`22422-22455`) он создаёт контейнер `+0xc` и вызывает
  `FUN_1404b1c0(DAT_14088df8, +0xc, +0x10, inv_name, 1)`.
  Путь собирает сам `FUN_1404b1c0` из `param_3` (буфер `scr_inv` в
  `this+0x2aac`, строка с `this+0x2ab0`; вызов передаёт `this+0x2ab0`,
  `decompiled.c:22454`; формат `scripts\inventory\%s.inv`,
  RVA `0x8e57c`; asm `0x1404b232-0x1404b239`). `this+0x388` — это
  путь `inv_name` в `FUN_14023aa0` (script/иной источник), не SEF.
- `FUN_1404b1c0` (RVA `0x4b1c0`): `param_1 = +0xc` (hot),
  `param_2 = +0x10` (main); R1 `51141`; pass 1 заполняет `+0xc`
  (`51177-51211`) через `coin(0.01*n3)` + `range(n4,n5)`, creation
  и direct count (merge возможен/`unverified`, chunk-loop нет); pass 2 заполняет
  `+0x10` (`51318-51366`) через `n3!=0` chance

  + `range` и creation с `this+4=0`. Оба прохода потребляют R2/R3
  (и R4/R5 для specials, out of scope). Порог метаданных `100000`
  (`0x186a0`, `51217`/`51373`), **не 4**; 4-stack exit нет. Точная
  таблица/asm — §15.2.

  (main). `RS_TestPersonHasItem`/`RS_GetItemCountI` читают
  `entity+0x10` (`p3b2a` §2.1/§2.2/§4.3) — поэтому **main = pass 2**
  обязателен; pass 1 (hot) можно не хранить, но его RNG обязан быть
  выполнен.
- Движение: RNG-вызовы не в конструкторе, а в update-тиках:
  `STAY_ROTATE rand(10,25)` — `FUN_1401c93c` `20759`;
  `RANDOM/RANDOM_RADIUS range` — `FUN_1401c2a0` `20410-20411`;
  `MOVED_FLIP coin` — `FUN_1401c93c` `20837`. В
  `FUN_1401edc4`/`FUN_1404b1c0` до лута нет вызовов
  `FUN_14006288`/`FUN_140061e4` для движения.
- Итог: **лут потребляет RNG раньше движения**; порядок сущностей —
  порядок `persons:` в SEF.
