## Per-frame конвейер (2026-10-23)

`GetClientAPI` (RVA `0xca88c`) отдаёт exe таблицу: `+0x4` init `0xc9cc0`,
`+0x8` shutdown `0xca0d0`, `+0xc` update `0xca210`, `+0x10` `0xca75c`.
Per-frame отрисовка уровня идёт из `0xc92bf` (внутри `0xc8e68`):

1. `FUN_120c8e68` (RVA `0xc8e68`) очищает счётчик `0x1211ab30` и собирает
   **список видимых объектов**:
   - массив указателей — `0x1211a930` = `DAT_12111360 + 0x95d0`;
   - счётчик — `0x1211ab30` = `DAT_12111360 + 0x97d0`;
   - ёмкость — `0x1211ab34` = `DAT_12111360 + 0x97d4` (инициализируется в `0x80`);
   - источник — клиентский массив сущностей `this+0x3d8`, количество `this+0x3e0`;
   - для каждой сущности вызывается виртуальный `[vtable+0xc](this+0x3f8)`;
     при истине указатель добавляется в список (не более ёмкости);
   - затем `FUN_120254d0` решает, видим ли кадр; при истине вызывается
     `FUN_1202effc` (RVA `0x2effc`).
2. `FUN_1202effc` — отрисовка кадра:
   - `FUN_1202d53c` — статики уровня: обход `world_vtable+0x40` (count) /
     `+0x24` (get); рисуются в **порядке списка**, без Y-sort; типы задаются
     старшими 16 битами `[object]`, строки путей —
     `levels\pack\%s\bitmaps\static\static_%d`, лог
     `Blitting static object: '%s'. Unknown blit flags.`;
   - `FUN_1202d984` — анимации уровня (LAO): обход `world_vtable+0x3c` /
     `+0x28`; путь `levels\pack\%s\data\animated\%s.lao`,
     кадры `levels\pack\%s\bitmaps\animated\anim_%d`; тоже в порядке списка;
   - `qsort(0x1211a930, 0x1211ab30, 4, FUN_1202bbdc)` — сортировка
     собранного списка сущностей (MSVC CRT `qsort`, RVA `0xe7e90`);
   - 9 проходов отрисовки `i = 0..8` через `FUN_1202df20` (jump table
     `0x12124d38`).

Следствия:

- Статики и LAO-анимации уровня **всегда рисуются до** динамических сущностей
  и между собой не сортируются по baseline — только порядок списка (в порте —
  порядок `number`).
- Персонажи рисуются **двумя проходами** (2 и 7), каждый идёт по уже
  отсортированному списку. То есть тени и тела — разные проходы, а не
  «тень непосредственно перед телом»; порядок задаёт baseline.
- Режим 2 (`FUN_1202e094`, проход 2) — **тень**: в `FUN_1202c424`
  ветка `kind == 2` (RVA `0x2c615`) дважды рисует спрайт с alpha `0.5`
  (`push 0x3f000000`). Режим 1 (`FUN_1202e148`, проход 7) — **тело**:
  ветка `kind == 1` (RVA `0x2c499`) рисует с alpha `1.0`
  (`push 0x3f800000`).

## Компаратор Y-sort

`FUN_1202bbdc` (RVA `0x2bbdc`) получает `qsort`-указатели на элементы списка,
разыменовывает их (`*p` = объект) и смотрит тип `type = [obj+0x14] & 0x3e`.
Таблица имён типов — `FUN_120c2484` (RVA `0xc2484`), строки в `.data1`
`0x121333a0`:

| type | строка | компаратор | ключ |
|---:|---|---|---|
| 2 | `EF_PERSON` | `FUN_1202ba40` | `[obj+0x1c]`, при равенстве `[obj+0x18]` |
| 4 | `EF_MAGIC` | `FUN_1202bb88` | `[obj+0x6cc]` |
| 8 | `EF_INVCONTAINER` | `FUN_1202bb10` | `[obj+0x1ac]`, если у обоих `[obj+0x24] == 0`, иначе `[obj+0x1a8]` |
| 0x10 | `EF_TRIGGER` | `FUN_1202bc30` | триггер всегда раньше нетриггера; два триггера равны |
| 0x20 | `EF_DOOR` | `FUN_1202bab0` | `[obj+0x3c4]` |
| прочее | — | — | 0 |

Для персонажа `+0x18` — X, `+0x1c` — Y: `FUN_12037a7e` (RVA `0x37a7e`)
перекладывает `+0x18/+0x1c` в `+0x404/+0x408` и выводит тайловые координаты
`+0x3c0/+0x3c4`. Сортировка — по Y, затем по X.

Что означают baseline-поля других типов (для будущих подпроектов):

- `EF_MAGIC`: `+0x6cc = [obj+0x1c] + [obj+0x38]` (`FUN_1203807b..0x380d8`);
  `+0x38` — вертикальный offset спрайта (низ/feet), т.е. baseline = Y + offset.
- `EF_DOOR`: `+0x3c4` — Y центра усреднённого bbox клеток
  (`FUN_12039000..0x3913e`); `+0x3c0` — X по той же формуле.
- `EF_INVCONTAINER`: `+0x1ac`/`+0x1a8` — две ветки baseline в зависимости от
  `+0x24`; семантика `+0x24` не извлечена.

Кросс-типовые сравнения не сводятся к одному ключу: компараторы добавляют
константы (`±2` для `EF_MAGIC` vs `EF_PERSON`, приоритет триггеров и т.п.).
Для порта с персонажами достаточно пары `(Y, X)`, но при добавлении
предметов/дверей/эффектов компаратор придётся воспроизводить целиком.

### Равные ключи

`qsort` — MSVC CRT (`FUN_120e7e90`); компаратор возвращает 0 при равенстве.
Порядок равных элементов `qsort` не гарантирует (не stable). Для двух
персонажей полное равенство `(Y, X)` означает совпадающую позицию (возможно
при `RANDOM*`, A3); порядок в оригинале зависит от исходного порядка массива
сущностей и внутренней реализации qsort. Порт может использовать
`std::stable_sort` (детерминированно сохраняет порядок массива) — это
осознанное решение для равных ключей, а не доказанный паритет.

## Анкоры и crops (PAD)

- PAD-загрузчик `FUN_1207d894` (RVA `0x7d894`) читает записи анимаций в
  структуры по `0x1c` байт (`this+0x3c + row*0x1c`).
- Поля записи, используемые отрисовкой/хит-тестом:
  `+0x44` — ширина кадра, `+0x48` — высота кадра, `+0x4c` — `anchorX`,
  `+0x50` — `anchorY`, `+0x54` — длительность/число кадров.
- `FUN_1207dc60` (RVA `0x7dc60`) вычисляет источник кадра из
  `frame*[+0x44]` и `[+0x48]` (полная ячейка кадра), без чтения crop-таблицы.
- `FUN_1207de4c` (RVA `0x7de4c`) для хит-теста берёт
  `pos - [+0x4c]/[+0x50] + offset`, т.е. **анкоры PAD используются как
  origin**: `draw = position - anchor`, как в порте.
- Crop-таблица PAD парсится (размер/строки), но в найденном пути отрисовки
  персонажа не применяется: источник — полная ячейка `frame_width x
  frame_height`. Это согласуется с P4a-замечанием, что для листов `l1_1`
  crop-прямоугольники не нужны. Утверждать «crops не нужны нигде» нельзя —
  путь для других типов спрайтов не проверен.

## Перекрытие статиком: cell mask, не Y-sort (Shot0001)

На `Shot0001.bmp` игрок (подсвечен зелёным) стоит на деревянной вышке/балконе
за перилами: нижняя часть спрайта невидима, перила перекрывают персонажа. Это
**не** объясняется Y-sort статиков:

- деревянная вышка и цирковая сцена уже присутствуют в
  `levels/pack/l1_1/bitmaps/layer.jpg` (проверено вырезкой фона в тех же
  координатах); фон рисуется до персонажей, значит перекрытие делает не
  порядок статик/персонаж;
- в `Client.dll` есть отдельный механизм клеточных масок:
  `FUN_1202bc54` (RVA `0x2bc54`) с debug-строками `ApplyCellMask:`,
  `Cell: %d, %d`, `Column: %d`, `cells:`; он читает массив клеток
  `renderer+0x8344`, границы `+0x95a0/+0x95a4`, пишет параметры маски в
  `0x121103e4…0x12110420`; вызов идёт из `FUN_1202c424` (перед отрисовкой
  спрайта). Консольные переменные `r_masks_show`, `r_masks_mode`,
  `r_masked_show` подтверждают слой масок;
- в LVL на тайл есть `u16 mask` (`LvlTile::mask`), а `BLK_MDSC` — список
  `LvlMask {number,x,y}`; порт их парсит, но **не использует** при отрисовке.

Вывод: порядок «статики → LAO → Y-sorted dynamic» остаётся верным для
порядка проходов, но видимое перекрытие персонажа статиком — это **клеточная
маска/foreground clip**, отдельная от Y-sort. В A7 она не реализована; текущий
порт нарисует игрока поверх перил. Нужна отдельная задача (A8) на разбор
семантики `tile.mask`/`BLK_MDSC` и `ApplyCellMask` + тест на `Shot0001`
(игрок за перилами не виден ниже линии маски).

## A8: cell mask / foreground occlusion (2026-10-23)

Причина перекрытия на `Shot0001` — маски, а не Y-sort.

- `BLK_MDSC` в `levels/lvl/l1_1.lvl`: **62** записи
  `(pad, number, x, y)`; `x/y` — пиксели мира, **левый верхний угол** маски.
  Для l1_1: `mask_45` — `number=45`, `x=885`, `y=1275`.
- Файл `levels/pack/l1_1/bitmaps/masks/mask_45.csx` — 687×741 RGBA:
  только два состояния, `(255,0,255,255)` (вне объекта) и `(0,0,0,0)`
  (силуэт объекта). `mask_45` — деревянная вышка; красная заливка
  alpha=0-пикселей по фону в (885,1275) **точно** совпала с вышкой в
  `layer.jpg` (проверено вырезкой). Значит, alpha=0 = occluding foreground,
  координаты — top-left.
- Другие примеры: `mask_1` 224×503 (решётка) при (136,416), `mask_40`
  272×218 (верёвки/флаги) при (1732,1303), `mask_44` 41×70 при (774,1111).
- В `Client.dll` маски применяются в `FUN_1202bc54` (`ApplyCellMask`) и
  `FUN_1202c424` (спрайт): `renderer+0x8344` — сетка ячеек/чанков
  (`+0x95a0=115`, `+0x95a4=112` для l1_1), `+0x8348` — служебный объект;
  debug-переменные `r_masks_show`, `r_masks_mode`, `r_masked_show`.
  Точная семантика флагов ячеек (`+0x8`/`+0xc`) и `ApplyCellMask` пока не
  извлечена; для A8 достаточно воспроизвести видимый foreground clip.
- Порт (реализовано): `LevelMask` в `Level`, загрузка `mask_<number>.csx`;
  `compose_mask_foreground` собирает текстуру «фон через alpha=0-силуэт»;
  `LevelScreen` вставляет маски в оба Y-отсортированных прохода
  (тени/тела) по baseline `y + height`, tie-break `x + width/2`; персонаж
  с меньшим baseline перекрывается, с большим — рисуется позже.
- Проверка: `mask_45` даёт ровно **182090** непрозрачных пикселей;
  `glview l1_1 --camera-x 885 --camera-y 1275` показывает вышку без
  «двоения»; сценарий `--place-person 0 100 180 --sim-ms 0` (персонаж за
  вышкой) даёт разницу >500 px между кадрами с `--no-masks` и без него.
  SHA-256: occluded `219D87D89FBCADE6F32A777971806F60813DE6A23B30D78595CA334432B701F0`,
  plain `E2A55F806CE2CBF8ECEF62FAC6DBF4DC6E176CC20A9B17FC7ADC6152A98DEFB6`.

## P4c: клик → диалог — реверс триггера (2026-10-23)

Источник: `Server.dll` v1.3 (`E3E0A262…`), image base `0x140000000`.

- Hero-объект (`this`) имеет очередь действий: `+0x200` — голова, `+0x204` —
  хвост, 32 записи по 16 байт (`index & 0x1f`), поля `+0..+0xc`; текущее
  действие — `+0x208..+0x214` (`FUN_1401f48c`).
- `FUN_1401f854` — постановка действия в очередь. Коды, найденные в
  `FUN_1401f48c`: `0x11` — `OnClick`-триггер объекта, `0x12` — диалог,
  `0x13`/`0x14` — прочие действия. Для `0x12` вызывается
  `CBServer::StartPersonDialog` (`FUN_1404410c`), которая проверяет тип
  `EF_PERSON` (2) и вызывает `CBDialogServer::OpenDialog`
  (`FUN_140441d8`) с именем диалога `person+0x2680`.
- `CBDialogServer::OpenDialog` проверяет: person валиден, `[person+0x150] == 0`,
  `[person+0x14fc] > 0`, нет активного диалога (`this+0x2cc == 0`); строит
  путь `scripts/dialogs/%s.cs`, грузит CS/globals/SDB, стартует VM. **Проверки
  расстояния/линии видимости в этом пути нет.**
- `OnClick` (`0x11`) — отдельный триггер (`FUN_1401f6bc`): если у объекта есть
  `OnClick`-скрипт, выполняется он; иначе для `EF_PERSON` ставится действие
  `0x12` (talk). Это объясняет, почему диалог открывается без distance-гейта
  на сервере.
- Клиентская часть (2026-10-23, `Client.dll` base `0x12000000`):
  - live-тест: один левый клик по дальнему стражнику → герой идёт к нему,
    затем **сам** открывается диалог; повторный клик не нужен. На
    `Shot0000.bmp` (SHA-256 `58E5054C…376C1F`) синий герой слева, коричневый
    стражник справа, между ними ~90 px; диалог уже открыт.
  - Курсор: `talk.ani` — ID `0xc` в таблице курсоров `0x121245c0`
    (`{id, path, flags}`, entry 18). Курсор talk ставится в `FUN_120c80a4`
    при `(entity+0x14 & 0x40) != 0` (`0x120c8142: push 0xc`), а также в
    `0x120c8355` при `entity+0x10 == -1`; иначе для контейнера — `0xe`
    (`take.ani`), для враждебного — `0x10`. Это подтверждает, что клиент
    различает «говорить» по флагу сущности, а не по расстоянию.
  - `gv_meet_offset` — конфиг-переменная `0x12106adc`, default `0.1`
    (`0x3dcccccd`, регистрация `0x12002a87`, строка `0x12122b58`). Рядом:
    `gv_monster_min_dist=12`, `gv_monster_max_dist=42`.
  - `gv_meet_offset` используется в `FUN_120b3464`/`FUN_120b3574`
    (refs `0x120b3557`, `0x120b35d0`): это **AI/meet-предикаты**, а не
    доказанный обработчик клика. Они считают величину из размеров кадров PAD
    (`FUN_12020400` — ширина кадра 12, `FUN_1201fab4` — высота кадра 15),
    тайла 12×9 и множителя `gv_meet_offset`; `FUN_12004880` трактует
    результат как вероятность/порог. Вызываются из debug/AI-панели
    `FUN_120b74f0`, где рядом есть `FUN_120b3390` (случайная свободная клетка)
    и `FUN_120b437c` (ходьба). Точная формула и роль в клике не доказаны.
  - Реальный путь клика ещё не изолирован. UI-event dispatcher
    `FUN_1203cfd0` (поля `+0x424..+0x430`, сеттер `FUN_120c7358`),
    обработчик hovered-объекта `FUN_120c80a4`, список объектов под курсором
    `FUN_120c84a8`. `FUN_120c8cbc` → `FUN_120c2fb0` — это **tooltip/координаты
    объекта** (форматирует `%d,%d` и т.п.), не обработчик клика. Клик по
    `EF_PERSON` нужно искать в dispatcher/ветках действий, а не здесь.
  - Следствие: «дистанция остановки» пока не извлечена; ~90 px на
    `Shot0000` может быть как выбранной клеткой, так и результатом
    pathfinding/occupancy. Вводить фиксированный радиус нельзя (D-029).
  - Ввод мыши находится **не в Client.dll**, а в `GoldenLand.exe`
    (SHA-256 `7854019E6C0A6C2BFDE6425C5799AFCA654D174A31CDAA7A624C3E17842109FF`):
    `FUN_0040ad04` читает состояние кнопок (`+0xf1c..+0xf2e`), считает edge-
    флаги (`+0xf40` — отпускание ЛКМ, `+0xf4c` — нажатие ЛКМ, `+0xf44/+0xf50`
    — ПКМ, `+0xf48/+0xf54` — СКМ), позицию (`+0xf94/+0xf98`), double-click
    (`+0xfb4/+0xfb8/+0xfc0/+0xfc4`) и порог `+0xfa4` из
    `gv_double_click_speed` (default `1.2`) × `gv_mouse_speed` (default `1.2`).
    Геттеры — `0x40c340` (`+0xf40`), `0x40c32c` (`+0xf44`), `0x40c354`
    (`+0xfc4`); vtable ввода — `0x47fd00` (метод обновления `+0x54`).
  - Кто читает геттеры и превращает клик в walk/talk: найдено в Client.dll.
    `CLevelScreen::update` (`0x1203f7e4`) вызывает `0x12041520`, который
    опрашивает input: берёт позицию (`input+0x00`), прибавляет камеру
    (`+0x18/+0x1c`), читает `input+0x30` (left release), `+0x34` (right
    release), `+0x2c`, `+0x44`, `+0x38/+0x3c/+0x40`; пишет в screen-объект
    `+0x50/+0x54` (mouse), `+0xb0` (left release), `+0xb4` (right release),
    `+0xb8` (middle), `+0x60/+0x64` и `+0x68/+0x6c/+0x70`.
  - `0x12040084` — left-click handler: если `[screen+0xb0]` и нет модификаторов,
    берёт `[screen+0x8c]` (entity), проверяет `entity+0x9c == 0x32`,
    `entity+0xc0` (action type 6/7) и попадание курсора (`entity vtable+0x40`);
    затем `0x12040c28` ставит в очередь команду:
    - action 6 → code `0x4f`, action 7 → `0x52`, иначе `0x45`;
    - правый клик (action 6) → `0x56`; ветки `0x46`/`0x49` — другие режимы.
    Очередь: узел 0x14 байт `{id, code, arg, ?, next}`, head `screen+0x4`;
    `0x12040c28` не дублирует code `0x4f`.
  - `0x12040f68` — right-click handler (аналогично, `[screen+0xb4]`).
  - Очередь читает `CLevelScreen::update` (`0x1203f7e4`): в конце он отдаёт
    head `[screen+0x4]` и обнуляет его. Wrapper `0x1204cf39` принимает список
    и для каждого узла вызывает `0x1203e3a8`; тот по `node+4` прыгает через
    таблицу `0x12126164` (коды `0x27..0x45`).
  - Для уровня отдельный обработчик `0x1205625c`: code `0x4f` →
    `0x1204bf94(entity id)`; также обрабатывает `0x56`, `0x46`, `0x47`,
    `0x41`, `0x4b`, `0x43`. `0x1204bf94` разбирает entity: ветка
    `entity+0x8 == 6` → `0x1204c361` (talk/действие), проверяет кадры героя
    `0x12`/`0x16`; `0x1204c4a8` выставляет `[level+0xc]=4` и зовёт
    `0x1204f06c`/`0x1204f09c`.
  - Клиентский локальный диалог: в `0x1205625c` при code `0x27` вызывается
    `0x1204c7ac` (открыть диалог), который зовёт `0x1204c464` (заполнение
    панели/строк) и проверяет `[0x12110ed4]+0x13c` (сеть) и
    `[0x12110ce0]+0x68` (текущий диалог). Т.е. клиент умеет открывать диалог
    **локально**, не дожидаясь server `0x12`/`OpenDialog`; server-путь —
    параллельная/сетевая ветка.
  - `gv_meet_offset` в этом пути не участвует — подтверждает, что он
    относится к AI/meet, а не к клику игрока. Для P4c достаточно локального
    overlay-диалога из `scr_dialog`; server `0x12` нужен для точного
    сетевого паритета, но не для отображения.
- SEF `points_entrance` порт пока не парсит; для hero-спавна нужен новый
  парсер. Путь диалога: `scripts/dialogs/` + `scr_dialog` + `.cs`
  (например, `l1_1\l1.p621...d621.age` → `scripts/dialogs/l1_1/...age.cs`).
- Вывод для P4c: серверный путь `0x12` не требует дистанции; клиент точно
  распознаёт talkable NPC по флагу `+0x14 & 0x40` и ставит курсор talk.
  Ходьба к NPC и последующий talk — отдельные шаги клиента, но точный
  обработчик клика ещё не доказан. Реализацию нельзя начинать с
  «правдоподобного» фиксированного радиуса (D-029); нужен либо дальнейший
  статический разбор `FUN_120c8cbc`/`FUN_120c2fb0`, либо live-замер.

## Открытые вопросы

1. Порядок равных ключей в MSVC `qsort` для реального массива сущностей
   (нужен live-снимок массива до/после сортировки).
2. Семантика `+0x24` у `EF_INVCONTAINER` (две ветки baseline).
3. Применяются ли PAD `crops` в других путях отрисовки (не person).
4. Скриншоты оригинала: NPC за/перед статикой/LAO-анимацией, высокий/низкий
   объект — manual gate.
5. P4c: обработчик клика по `EF_PERSON` в UI-event dispatcher
   `FUN_1203cfd0`/ветках действий; как он выбирает клетку/ходьбу и когда
   ставит talk `0x12`. `FUN_120c8cbc`/`FUN_120c2fb0` — tooltip, не клик.
   Дополнительно: роль `FUN_120b3464`/`FUN_120b3574` (`gv_meet_offset`) —
   AI/meet-предикаты или часть клика; нужен live-снимок позиции героя, цели
   и выбранной клетки после клика.

## Ограничения

- Подбирать порядок визуально без вывода из `Client.dll` запрещено (AGENTS/D-029).
- `crops` проверены только для листов `l1_1` (см. `formats.md`) и только для
  person-пути; это не общее правило.
