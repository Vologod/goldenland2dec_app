# P5 — Effect runtime core: aging, client filter, save persistence

Дата: 2026-11-26. Статус: research done.

Источник: `Server.dll` SHA-256
`418E256063748F2E90DB35AE7C6ABE6EAC401FB86908CB5F27EBF565A21CC837`
(`ImageBase = 0x14000000`) и `Client.dll` SHA-256
`FBF213B4B820E767A529556D0F7E4D29EE2202E7E39C3E49043F49D55DAB5C16`
(`ImageBase = 0x12000000`); `RVA = VA − ImageBase`. Инструменты:
`llvm-objdump -d --x86-asm-syntax=intel`, `.local/decomp/{server,client}`,
корпус сейвов `I:\Games\Златогорье-2\Saves\slot*.sav`.

Закрывает остаток P5c2b §3.1: канал активных эффектов персоны
(записи 5×int32), их клиентский фильтр и старение по игровому времени,
а также персистентность в сейве. Продюсеры (зелья/еда/магия) — вне scope.

## 1. Формат записи

Запись — 5 слов `0x14` байт: `{+0 id, +4 int32 value, +8 uint32 flags,
+0xc uint32 cond, +0x10 int32 extra}`. Это тот же формат, что ITM-effect /
модификатор экипировки (`docs/research/p5c2-armor-weight-extraction.md`).

Серверный список персоны: данные `+0x110C`, count `+0x14F4`, capacity
`+0x14F8` (`FUN_14018848`, RVA `0x18848`; `FUN_1401792c`, RVA `0x1792c`,
добавляет при `count < 0x32` и `count < capacity`). Травма
`RS_SetInjured` пишет ключ `{22,-49,129,0,-1}` (`FUN_14018848`).

## 2. Старение — `FUN_1405719c` (RVA `0x5719c`)

**Коррекция:** `docs/research/p5c2b-residual-conditions.md` §3.1 ссылался на
RVA `0x57954`. Это другая функция (`FUN_14057954` копирует `0x47` dword в
`+0xff0`, к эффектам не относится). Реальное старение — внутри
`FUN_1405719c` (size `1975`), блок эффектов в дизассемблере
`0x140577c9..0x14057953`.

Вход — `param_2` (8 dword текущего datetime). В начале тика
`FUN_14019584` (RVA `0x19584`) копирует `param_2` в `+0xf9c..0xfb8`
(3-й `0x20`-snapshot). Дельта считается как
`current − previous` через time-vtable (`DAT_14088e14+4`), затем
`elapsed = (day*24 + hour)*60 + minute` (минуты; секунды отбрасываются).
Если `elapsed == 0` — выход (`0x140577b8`).

Упаковка `cond`:

- младшее слово (`0x10`-ветка и задержка `0x20`): `b0 = часы`,
  `b1 = минуты`, т.е. `minutes = (cond & 0xff)*60 + ((cond>>8) & 0xff)`;
- старшее слово (активная длительность `0x20`): `b2 = часы`,
  `b3 = минуты`, т.е. `((cond>>16) & 0xff)*60 + ((cond>>24) & 0xff)`.

Ветки (подтверждено дизасмом):

- `flags & 0x10` (`0x140577da..0x1405783e`): длительность в младшем слове.
  Если `elapsed >= dur` → удалить запись (`call FUN_1401798c`, сдвиг);
  иначе `cond = (rem/60) | ((rem%60)<<8)` — **весь dword** перезаписывается,
  старшее слово затирается.
- `flags & 0x20` (`0x1405785c..0x1405792f`):
  - `(cond & 0xffff) != 0` → это задержка. `elapsed >= delay` →
    `cond &= 0xffff0000` (младшее слово обнуляется, эффект становится
    активным); иначе вычитание и перепаковка младшего слова с сохранением
    старшего (`and ecx,0xffff0000; or`).
  - `(cond & 0xffff) == 0` → активная длительность в старшем слове.
    `elapsed >= dur` → удалить; иначе `cond = (rem/60)<<16 | (rem%60)<<24`
    (весь dword).
- `0x10`-ветка по `0x1405783c` прыгает на проверку `0x20`, т.е. при обоих
  битах применяются обе ветки (на уже обновлённом `cond`).

## 3. Клиентский фильтр — `FUN_120b0690` (RVA `0xb0690`)

Дизасм `0x120b0690..0x120b07f9`:

- проверяет, что wrapper относится к локальному игроку
  (`[ebp+0x14] ==` id из `DAT_12110f28` через `FUN_120c54dc`);
- перебирает `DAT_12110f28+0x6DC`, count `+0x6E0`;
- для записи `flags = [+8]`: если `(flags & 0x20)` и `(cond & 0xffff) != 0`
  → `jne 0x120b07d7` (пропустить и перейти к следующей);
- иначе копирует все 5 слов в контейнер модификаторов (`wrapper+0x40`)
  через битмап свободных слотов.

Следствие: «задержанный, но ещё не наступивший» эффект (младшее слово
задержки ненулевое) в статах не участвует; активные и `0x10`-эффекты
применяются полностью.

## 4. Персистентность в сейве

- **BT_HERO**: writer `FUN_1401e690` (RVA `0x1e690`) заканчивается вызовом
  `FUN_1401d84c` (RVA `0x1d84c`): пишет 4×`0x20` time-snapshot по
  `+0xf5c/+0xf7c/+0xf9c/+0xfbc`, затем `u32 count` + `count*0x14` записей
  из `+0x110C`. Reader `FUN_1401d8bc` (RVA `0x1d8bc`) зеркален.
- **Type-2 person (BT_ENTS tail)**: тот же хвост
  `0x80 + u32 count + count*0x14` (`docs/research/p2-15c3a-write-back.md`
  §4.2 п.27; `src/game/src/save_person.cpp`).
- Порт уже моделирует обе формы как raw: `assets::HeroSaveBody::tail80`
  (`0x80`) + `extra`; `game::SavePersonRecord::tail80` + `extra`.
- Часы эффектов — 3-й snapshot `+0xf9c`, т.е. `tail80[0x40..0x60]`
  (`FUN_14019584` пишет 8 dword начиная с `+0xf9c`).

## 5. Реальный оракул (28 сейвов)

Скан BT_HERO всех `slot*.sav` (Python, zlib после 112-байтного заголовка):
hero `extra` count — 27 сейвов `0`, `slot16.sav` — `1`:

```
words = {9, -3, 0x60, 0x23000000, -1}
```

Разбор: `id=9` (DEX), `value=-3` (flat `0x40`), `flags=0x60` (`0x40|0x20`),
`cond=0x23000000`: младшее слово `0` → активная фаза, длительность
`b2*60 + b3 = 0*60 + 35 = 35` игровых минут. Snapshot’ы `slot16`:
`0/1` — нули, `2` (`+0xf9c`) — `1124-11-27 04:00:31.009`,
`3` (`+0xfbc`) — `1124-11-27 04:00:30.020`.

Значит на загруженном `slot16` клиент должен применить DEX−3 (задержка не
висит), а через 35 игровых минут эффект удаляется. Это проверяемый
real-оракул для статов и старения.

NPC type-2 `extra` в этом скане не разбирались; их покроет real-тест
round-trip (парсер уже есть в `save_person.cpp`).

## 6. Открытые/вне scope

- `0x10|0x20` одновременно: оригинал применяет обе ветки; в данных не
  наблюдалось.
- Snapshot’ы `0/1/3` (`+0xf5c/+0xf7c/+0xfbc`) вне эффектов (регенерация и
  пр.) — не трогаем.
- Интервал `0x8` — не реализуется (0 в ITM-корпусе, как в P5c2b).
- Продюсеры эффектов: зелья/еда/магия (`LE_CastMagic`), `LE_CastEffect` —
  отдельные инкременты.
