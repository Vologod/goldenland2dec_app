# Design: Goldenland 2 → Android (native port)

Статус: **на ревью**.
Дата: 2026-10-19.
Целевая игра: «Златогорье 2» v1.3 (GoldenLand engine), `I:\Games\Златогорье-2`.

## 1. Контекст и цель

Нужен нативный порт «Златогорья 2» на Android с полной одиночной кампанией.
Исходников движка нет. Есть бинарники `GoldenLand.exe` + `Client.dll` + `Server.dll`
и обширная документация форматов от сообщества.

Цель проекта — переносимый исходник движка (C++20), который читает оригинальные данные
игры и воспроизводит её поведение, с нативной сборкой под Android через SDL2.

## 2. Границы

Входит:

- Полная одиночная кампания на Android.
- Реконструкция клиентской и серверной логики, скриптовой машины, рендера, UI, звука.
- Чтение оригинальных `.pak`/`.scr`/`.csx`/`.sdb`/`.itm`/уровней во время выполнения.

Не входит:

- Распространение ассетов игры.
- Обход DRM/StarForce; запуск оригинальных бинарников.
- Мультиплеер в первой версии (граница `ServerCore`/`ClientCore` сохраняется).
- Модификации контента и редактор.

## 3. Стратегия и альтернативы

Выбрано: **чистая реконструкция движка на переносимом C++20 + SDL2**.
Логика восстанавливается по декомпиляции (`Ghidra`) и документации; оригинальная игра
на Windows используется как поведенческий эталон (oracle). Данные переиспользуются как есть.

Рассмотренные альтернативы:

| Вариант | Плюсы | Минусы | Вердикт |
|---|---|---|---|
| Сборка машинного декомпила «как есть» | Максимальная близость к оригиналу | Вывод Ghidra/IDA для MSVC C++ не собирается без массовой ручной чистки; фактически та же реконструкция, но грязнее | отклонён |
| Гибрид: эмуляция x86 DLL + SDL2-shims | Быстрый запуск, точное поведение | Нет исходника; JIT x86 на Android, сложная отладка; противоречит цели | отклонён |
| Чистая реконструкция C++/SDL2 | Поддерживаемый код, нативный Android, чистые слои | Большой объём, риск расхождений | **выбран** |

## 4. Архитектура

### 4.1 Слои и зависимости

Зависимости только вниз:

```
platform → app → game / render / ui / audio → script / core → assets
```

- `assets` — VFS и чистая библиотека форматов: стандартная библиотека (включая
  `std::filesystem`) + miniz + stb. Без SDL, платформенных API и глобального состояния.
- `core` — цикл, конфиг `.ini`, консоль/команды, события.
- `script` — CS bytecode VM, AgeScript, нативные биндинги (`RS_*`, `D_*`, `WD_*`, ...).
- `game` — мир, персонажи, предметы, локации, системы (движение, бой, магия, квесты).
- `render` — SDL2/OpenGL ES: палитровые текстуры, спрайты, изометрия, камера.
- `ui` — экраны, диалоги, HUD, тач-раскладка.
- `audio` — музыка/звук (SDL_mixer/OpenAL).
- `app` — состояния приложения, загрузка игры, сохранения.
- `platform` — окно, ввод, время, ФС, логирование, жизненный цикл Android.

### 4.2 Соответствие оригиналу

| Оригинал | Реконструкция |
|---|---|
| `Server.dll` | `game/` + `script/` (симуляция, логика, скрипты) |
| `Client.dll` | `render/` + `ui/` + `audio/` (представление, ввод) |
| `GoldenLand.exe` | `app/` + `platform/` + `core/` (хост, цикл, консоль) |

`ServerCore` и `ClientCore` — явные интерфейсы. В одиночной игре оба работают в одном
процессе и общаются напрямую (без сокетов), но граница сохраняется для будущего мультиплеера.

### 4.3 Поток данных

```
game_dir
  → GameVfs (loose files + *.pak + *.update.N.pak)
  → assets-декодеры (pak/csx/sdb/itm/lvl/...)
  → game-мир и script-VM (ServerCore)
  → состояние
  → ClientCore (render/ui/audio) → экран/динамик
  ← ввод (тач/клавиатура/мышь/геймпад) → команды → ServerCore
```

## 6. P0 — Ассеты и форматы (детальный дизайн)

### 6.1 Цель

Библиотека `gl_assets` и CLI `glpak`, которые читают целевые архивы, распаковывают файлы
и декодируют базовые форматы. P0 не содержит рендера и не зависит от платформы.

### 6.2 Тулчейн и сборка

- CMake ≥ 3.20, Ninja, C++20.
- Windows x64: MSVC 2022 Build Tools (рекомендуется) или LLVM-MinGW/Clang.
- Вендоренные зависимости: `miniz` (zlib), `stb_image` + `stb_image_write` (BMP/PNG),
  `doctest` (тесты).
- CMake-опции: `GL_BUILD_TESTS` (ON), `GL_BUILD_TOOLS` (ON).
- `gl_assets` не использует SDL и платформенные API (допустима стандартная библиотека,
  включая `std::filesystem`); `glpak` — desktop-only.

### 6.3 Структура

```
CMakeLists.txt
cmake/CompilerWarnings.cmake
third_party/miniz/
third_party/stb/
third_party/doctest/
src/assets/include/gl/assets/*.hpp
src/assets/src/*.cpp
tools/glpak/main.cpp
tests/assets/*.cpp
```

### 6.4 Модули и API

- `bytes.hpp` — `using Bytes = std::vector<std::uint8_t>;`
- `result.hpp` — `Result<T>` на `std::variant<T, Error>`; `Error { code, message }`.
  Через границы модулей исключения не летят.
- `log.hpp` — `gl::log(level, ...)` с уровнями `debug/info/warning/error`.
- `cp1251.hpp` — `std::string to_utf8(std::span<const std::uint8_t>)`,
  `std::string casefold_cp1251(std::string_view)`.
- `pak.hpp` — `PakArchive`: `open_from_file`, `open_from_memory`, `entries`, `find`, `read`.
  Проверяет magic, границы FAT, перекрытия/дубликаты; лимит распакованного файла 512 МиБ.
- `vfs.hpp` — `GameVfs::mount(game_dir)`:
  - сканирует `<game_dir>` и `<game_dir>/Data` на `*.pak`;
  - приоритет: loose-файл > `*.update.N.pak` (по убыванию N) > базовый `*.pak`;
  - ключи нормализуются: `\` → `/`, casefold cp1251;
  - `exists`, `read`, `list`.
- `csx.hpp` — `CsxImage { width, height, transparent_bgr, palette, indexed, rgba }`;
  `decode_csx` с проверкой монотонности `row_offsets` и точного заполнения строк.
- `sdb.hpp` — `Sdb` (map `uint32 → std::string` в UTF-8); сигнатура `SDB ` опциональна;
  без сигнатуры строковые байты XOR `0xAA`.
- `itm.hpp` — `Item` со всеми полями из `docs/research/formats.md`;
  условные блоки разбираются по флагам/типу.
- `image.hpp` — `Image { width, height, rgba }` через `stb_image` (BMP/PNG/JPG).
- `pak` использует `miniz` (`mz_uncompress`): FAT `size` — несжатый размер; по `offset`
  лежит `mode : uint32`: `0` — raw ровно `size` байт, иначе — `stored : uint32` + zlib-поток
  длиной `stored`, разворачивающийся до `size` (подтверждено на реальных архивах, D-013).

### 6.5 CLI `glpak`

```
glpak info <game_dir>
glpak list <game_dir> [--archive <name>]
glpak extract <game_dir> --all --out <dir>
glpak extract <game_dir> --file <virtual/path> --out <dir>
glpak extract <game_dir> --prefix <prefix> --out <dir>
glpak decode-csx <game_dir> --file <path> --out <png>
glpak decode-sdb <game_dir> --file <path> --out <txt>
glpak decode-itm <game_dir> --file <path>
```

Коды возврата: `0` успех, `1` ошибка аргументов, `2` I/O, `3` формат, `4` несовпадение эталона.

### 6.6 Обработка ошибок

- Все входные файлы считаются недоверенными: проверяются длины, смещения, границы,
  лимиты аллокаций.
- Ошибка содержит контекст: архив, имя файла, offset, ожидаемое/фактическое.
- Один битый файл не должен ронять `extract --all`: он логируется, остальные обрабатываются;
  итоговый код `3`, если были ошибки формата.

### 6.7 Тестирование

Unit (без данных игры, синтетические байты):

- PAK: raw и zlib записи, битый magic/count/offset, дубликаты.
- VFS: приоритет loose > update N > base, casefold, разделители.
- CSX: палитра, прозрачность, RLE, битые offsets.
- SDB: с сигнатурой и без (XOR), пустые строки.
- ITM: несколько типов/флагов, опциональные блоки.
- cp1251 ↔ UTF-8.

Integration (включаются только при заданном `GL_GAME_DIR`; рекомендуемое значение —
`I:\Games\Златогорье-2`):

- открытие всех 15 архивов;
- количества: `scripts.pak` 4485, `sdb.pak` 45, `items.pak` 3786, `engineres.pak` 1041;
- суммарные размеры: scripts 9 324 686, sdb 1 411 188, items 28 847 595;
- для остальных архивов эталонные количества и размеры фиксируются в
  `docs/research/00-game-build.md` после первого успешного прогона и проверяются на повторяемость;
- чтение и декодирование выборки каждого типа; отсутствие ошибок на **всех** `.csx`, `.sdb`, `.itm`.

Приёмочный прогон (фиксируется в `STATUS.md`):

- `glpak extract --all` во временный каталог; сверка количества файлов и размеров по архивам;
- `glpak decode-csx` нескольких спрайтов; PNG открывается визуально;
- `ctest` зелёный.

### 6.8 Критерии готовности P0

1. Сборка на Windows x64 (CMake + Ninja) с включёнными предупреждениями
   (`/W4` для MSVC, `-Wall -Wextra` для Clang) и без предупреждений.
2. `glpak info` видит все архивы и корректные количества.
3. Полная распаковка: для `scripts`/`sdb`/`items`/`engineres` — точное совпадение
   с эталонными значениями; для остальных архивов — совпадение с зафиксированным
   эталоном и повторяемость.
4. Все `.csx`, `.sdb`, `.itm` целевой сборки декодируются без ошибок.
5. Unit- и integration-тесты зелёные.
6. `gl_assets` не содержит включений SDL/Windows (проверка grep в тесте/скрипте).
7. Обновлены `STATUS.md`, `PROJECT.md`, `docs/research/`.

### 6.9 Вне P0

`LVL`, `PAD`, `MDF`, `ANI`, `SEF`, `LAO`, скрипты `SCR`/`CS`, рендер, звук, Android.
Они входят в P1–P9.

## 7. Сохранение контекста между задачами

Источник истины — только `docs/`. Протокол:

1. Перед задачей обновить `STATUS.md`: задача, критерии, команды проверки.
2. Во время работы факты (RVA, offset, формат, поведение) писать в `docs/research/`
   с источником: файл, хэш, RVA/offset, инструмент.
3. После задачи обновить `STATUS.md` (сделано, чем проверено, дальше),
   `PROJECT.md` (статус подпроекта), при решении — `DECISIONS.md`.
4. Один подпроект за задачу; смешивание запрещено.
5. Definition of Done включает реально выполненные команды и их вывод.
6. Открытые вопросы — только в `STATUS.md` → Open Questions.

## 8. Тестирование проекта (стратегия)

- Модульные тесты на каждый декодер/систему.
- Интеграционные тесты на реальных данных (гейт по каталогу игры).
- Поведенческий эталон: оригинальная игра на Windows; сравнение через консольные
  команды (`d_location`, `d_info_persons`, `gv_Title` и т.п.) и сохранения.
- Визуальная регрессия рендера — с P1 (скриншоты-эталоны).
- Детерминизм серверного тика — с P2/P5.

## 9. Риски и снижение

| Риск | Снижение |
|---|---|
| Документация форматов неполная/неверная | Проверка на всех файлах; сверка с кодом `GoldenLandEditor`/`Xcsx.dpr`; фиксация расхождений в research |
| Сложность RLE в CSX | Реализация по `Xcsx.dpr`; пиксельные тесты и визуальная проверка |
| Объём проекта | Декомпозиция; строго один подпроект за задачу |
| Расхождение поведения с оригиналом | Oracle-прогоны на Windows, сравнение состояний и логов |
| Неизвестная семантика байткода `.cs` | Постепенный reverse engineering `Server.dll` + опкоды из `GoldenLandEditor` |
| Правовые ограничения | Только чтение данных пользователя; никаких ассетов в репозитории; без DRM |
| Большие архивы (402 МБ, 327 МБ) | Потоковое чтение, только FAT в память, лимиты |
| Производительность на Android | Ранний профилинг в P1, палитровые текстуры, атласы, GLES |
| Отсутствие тулчейна на машине | Установка CMake/Ninja/компилятора — первый шаг P0 |
