# A7: Y-sort, анкоры и crops — дизайн

## 1. Цель

Привести порядок отрисовки уровня в порте к `Client.dll` v1.3: динамические
сущности (сейчас — персонажи) рисуются по baseline, тени и тела — отдельными
проходами; статики и LAO-анимации сохраняют оригинальный порядок проходов.
Анкоры и источник кадра персонажа остаются такими же, как в оригинале.

Основание: `docs/research/p4b2-render-order.md` (SHA-256 `Client.dll`
`FBF213B4…AB5C16`), D-029.

## 2. Поведение оригинала (извлечено)

- `FUN_120c8e68` собирает список видимых сущностей (`DAT_12111360 + 0x95d0`,
  счётчик `+0x97d0`, ёмкость `+0x97d4 = 128`), обходя клиентский массив
  `this+0x3d8`/`+0x3e0` и вызывая виртуальный `[vtable+0xc](this+0x3f8)`.
- `FUN_1202effc` в одном кадре:
  1. рисует статики уровня (`FUN_1202d53c`) в порядке списка;
  2. рисует LAO-анимации (`FUN_1202d984`) в порядке списка;
  3. сортирует список сущностей `qsort` с компаратором `FUN_1202bbdc`;
  4. выполняет 9 проходов `FUN_1202df20`.
- Для `EF_PERSON` (type `2`) ключ: `[obj+0x1c]` (Y), при равенстве `[obj+0x18]`
  (X). Проход 2 (`FUN_1202e094`, режим 2) — тень (alpha 0.5), проход 7
  (`FUN_1202e148`, режим 1) — тело (alpha 1.0). Оба прохода идут по одному и
  тому же отсортированному списку.
- `qsort` — MSVC CRT; для равных ключей порядок не гарантирован (unstable).
- Анкоры: PAD `anchor_x/anchor_y`; origin = `position - anchor`. Источник кадра
  — полная ячейка `frame_width x frame_height`; crop-таблица PAD в person-пути
  не применяется.
- Статики/анимации не сортируются по baseline и всегда рисуются до
  динамических сущностей.

## 3. Границы

Входит:

- порядок отрисовки персонажей в `LevelScreen`;
- два прохода (тени, тела);
- чистые функции ключа/сортировки и прямоугольника кадра;
- тесты и документация.

Не входит:

- `EF_MAGIC` (4), `EF_INVCONTAINER` (8), `EF_TRIGGER` (0x10), `EF_DOOR` (0x20) —
  в порте их ещё нет; кросс-типовые сравнения зафиксированы в research для
  будущих подпроектов;
- изменение парсинга PAD, текстур и симуляции движения;
- сортировка статиков/LAO-анимаций (оригинал её не делает);
- воспроизведение нестабильного порядка MSVC `qsort` для полного равенства
  ключей;
- **cell mask / foreground clip** (`ApplyCellMask`, LVL `tile.mask`,
  `BLK_MDSC`, `r_masks_*`) — по `Shot0001` именно маска перекрывает игрока
  перилами статика; это отдельная задача **A8**, не Y-sort.

## 4. Архитектура

Слой `app` (представление), без изменений в `game`/`assets`.

### 4.1 `gl::app::person_render`

Новые типы и функции (SDL-free, тестируются в `tests/app/test_person_render.cpp`):

```cpp
struct PersonDrawKey {
    float x = 0.0f;
    float y = 0.0f;
};

struct FrameRect {
    int x = 0;
    int y = 0;
    int w = 0;
    int h = 0;
};

std::vector<std::size_t> sort_person_indices(std::span<const PersonDrawKey> keys);

FrameRect frame_rect(std::size_t column, std::size_t row,
                     int frame_width, int frame_height);
```

- `sort_person_indices`: `std::stable_sort` по `(y, x)`; возвращает индексы
  исходного массива. При полном равенстве сохраняется порядок входа
  (детерминизм порта; оригинальный `qsort` unstable).
- `frame_rect`: `x = column*frame_width`, `y = row*frame_height`,
  `w = frame_width`, `h = frame_height`; crop-таблица не участвует.

### 4.2 `LevelScreen`

- `enum class PersonPass { shadow, body }` (внутри `level_screen.hpp`).
- `draw_person(..., PersonPass pass, std::uint64_t elapsed_ms)`:
  выбирает анимацию/текстуру/направление/кадр один раз и рисует только
  запрошенный слой.
- `render`: после `simulation_.advance` строит `std::vector<PersonDrawKey>` из
  `simulation_.persons()[person.instance]` (X = `movement.x`, Y = `movement.y`)
  и один раз сортирует индексы. Затем:
  1. проход `shadow` по отсортированным индексам;
  2. проход `body` по тем же индексам.
- Статики и анимации остаются до этих проходов в текущем порядке.
- Буферы ключей/порядка — члены `LevelScreen`, чтобы не аллоцировать каждый
  кадр.

### 4.3 Анкоры и crops

Поведение не меняется: `place_person_px`/`place_person_shadow_px` вычитают
PAD-анкоры; `frame_rect` возвращает полную ячейку. Это закрепляется тестами,
чтобы A7 не «улучшил» поведение визуально.

## 5. Тесты

Unit (`gl_person_render_tests`):

- сортировка по Y, затем X;
- стабильность при равных `(Y, X)`;
- `frame_rect` для колонки/строки и ненулевых размеров;
- существующие тесты анкоров остаются зелёными.

Integration / real:

- `glview l1_1 --sim-ms 0` и `--sim-ms 10000` — exit 0, PNG 1280×720,
  детерминизм повторного прогона;
- `gl_game_tests` real `l1_1` — без регрессий;
- ручной гейт: 2–3 скриншота оригинала (NPC за/перед статикой, два NPC на
  близком Y, высокий объект) + кадр порта; проверить, что NPC меняют порядок
  при пересечении baseline.

## 6. Приёмка

- `cmake --build build` — успех.
- `ctest --test-dir build --output-on-failure` с `GL_GAME_DIR` — все тесты.
- Новые unit-тесты падают до реализации и проходят после.
- Скриншоты оригинала приложены к отчёту; расхождений порядка нет.
- `docs/research/p4b2-render-order.md`, `docs/DECISIONS.md`, `docs/STATUS.md`
  обновлены.

## 7. Риски и открытые вопросы

- Оригинал сравнивает целочисленные `+0x1c/+0x18`; порт сортирует float
  `movement.x/y`. Для различных позиций результат совпадает; при разнице
  меньше 1 px возможен другой порядок. Правило округления клиента не
  извлечено — вынесено в Open Questions research.
- Полное равенство `(Y, X)` (персонажи на одной позиции) в оригинале зависит
  от `qsort`; порт детерминированно сохраняет порядок массива.
- Проходы 2/7 доказаны по alpha 0.5/1.0, но порядок остальных типов
  (`EF_MAGIC` и др.) в порте пока не реализуется.
